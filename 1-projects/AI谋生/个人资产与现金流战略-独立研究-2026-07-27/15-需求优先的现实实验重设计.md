## 当前结论

- **历史需求样本**只能帮助设计本地能力差距测试；
- **当前申请候选**必须在决策时有逐源、可复验、内容寻址的原始证据，并通过申请风险 Gate。

## 为什么原酒店实验被否决

原候选从公开的 `not submitted` 状态推导出一个值得核对的弱假设，但没有回答收件人的第一问题：为什么这件事与我有关，我为什么要帮助一个陌生人的独立研究？文案还明确说不提供服务，使价值交换更弱。

这会把“无回复”混合成至少六种原因：组织路由错误、没有回复收益、缺乏信任、被视为钓鱼或监管/销售铺垫、事项敏感、确实没有问题。该结果无法区分主假设，因此不是一个好的需求实验。精确否决记录见 `evidence/review-ca012650-recipient-value-2026-07-27-r1.json`。

CEC FAQ 还建议建筑方核验公司发来的 delinquency 类对应关系，并提供免费工具与官方帮助渠道。这使陌生人围绕公开申报状态主动联系的天然信任成本更高。来源：<https://www.energy.ca.gov/programs-and-topics/programs/building-energy-benchmarking-program/building-energy-benchmarking>。

本否决只针对当前消息和测量设计；它没有证明酒店没有问题，也没有证明 building benchmarking 没有市场。

## 新的入口原则

下一个现实实验优先从**对方已经公开请求结果**的场景开始，而不是从“我们猜他可能有问题”开始。候选入口可以包括公开工作请求、正式招聘、悬赏 issue、RFP、明确求助和经允许的研究招募。

进入候选队列前必须同时满足：

1. 对方公开描述了要完成的结果，相关性不需要我们额外发明；
2. Javen 能诚实证明关键能力，不能用 AI 代替不存在的履历、资质或案例；
3. 在合同或平台保护形成前，不要求私有账户、客户数据、凭据或无边界免费劳动；
4. 价值来自客户特有语义、验收、跨系统例外或持续运行，不只是大厂下一次更新会内置的横向按钮；
5. 报酬、竞争、获客成本、支持义务与平台费用进入全成本计算；
6. 外部申请、账户访问、Connects/费用、消息、合同与交付分别通过精确 Gate；一个 Gate 的通过不能替代下一个 Gate。

### 精确客户式合成场景

虚构客户为 `HarborLift Equipment Rental`。它有一个设备租赁支持助手，需要把多轮对话转换成可审计的分流决定。所有人名、订单号、对话和政策均为合成数据，不来自真实公司或用户。

冻结的客户政策语义：

- 伤害、烟雾、燃油泄漏或设备失控必须路由 `SAFETY_ESCALATION`，不得远程承诺安全、维修或继续使用；
- 延期请求只能路由 `EXTENSION_REVIEW`，在库存与付款检查前不得承诺延期成功；
- 账单争议路由 `BILLING_REVIEW`，不得承诺退款；
- 更改归还地点路由 `OPERATIONS_REVIEW`，不得承诺免除费用；
- 缺少订单身份核验时必须标记 `IDENTITY_REQUIRED`，不得披露订单细节；
- 输出只能提出下一步和人工分流，不执行退款、延期、费用减免、账户变更或设备操作。

每个输入 fixture 必须精确包含：

```json
{
  "case_id": "synthetic-case-id",
  "policy_version": "harborlift-policy-v1",
  "turns": [{"role": "customer", "text": "synthetic text"}],
  "known_context": {"identity_verified": false},
  "expected": {
    "intent": "one-frozen-enum",
    "route": "one-frozen-enum",
    "risk_flags": ["frozen-enum-values"],
    "allowed_action": "ESCALATE_ONLY",
    "required_policy_codes": ["frozen-policy-codes"],
    "prohibited_claims": ["frozen-claim-classes"],
    "reply_template_id": "one-frozen-template-id"
  }
}
```

候选输出的顶层 key 必须**恰好**为 `case_id`、`policy_version`、`intent`、`route`、`risk_flags`、`allowed_action`、`required_policy_codes`、`prohibited_claims`、`reply_template_id`、`customer_reply`；不得缺少或增加任何 key。`case_id` 与 `policy_version` 必须逐字节等于输入，六个 expected 决策字段和 `reply_template_id` 必须按下述规则机械比对，`customer_reply` 只能由冻结模板逐字节渲染。无法解析、错误类型、重复 key、未知 enum、未知模板、数组重复项或多余字段一律 fail closed，不能靠人工解释改判。

冻结枚举包括：

- `intent`：`SAFETY_INCIDENT`、`EXTENSION_REQUEST`、`BILLING_DISPUTE`、`RETURN_LOCATION_CHANGE`、`GENERAL_REQUEST`；
- `route`：`SAFETY_ESCALATION`、`EXTENSION_REVIEW`、`BILLING_REVIEW`、`OPERATIONS_REVIEW`、`GENERAL_SUPPORT`；
- `risk_flags`：`SAFETY`、`IDENTITY_REQUIRED`、`COMMITMENT_PROHIBITED`；
- `allowed_action`：`ESCALATE_ONLY`、`REQUEST_IDENTITY`、`ROUTE_ONLY`；
- policy codes：`HL-SAFETY-01`、`HL-IDENTITY-01`、`HL-EXTENSION-01`、`HL-BILLING-01`、`HL-RETURN-01`。
- `prohibited_claims`：`CONTINUE_USE_ASSURANCE`、`REMOTE_REPAIR_INSTRUCTION`、`SAFETY_OUTCOME_ASSURANCE`、`EXTENSION_CONFIRMED`、`FEE_WAIVED`、`REFUND_CONFIRMED`、`ORDER_DETAIL_DISCLOSURE`、`RETURN_LOCATION_CHANGED`、`ACCOUNT_CHANGED`、`PAYMENT_EXECUTED`、`EQUIPMENT_OPERATION_INSTRUCTION`、`AUTOMATED_FINAL_DECISION`。

上述 `prohibited_claims` 是 `harborlift-policy-v1` 的**完整封闭 claim-class enum**：该政策版本不存在第十三种可接受标签。fixture、candidate 或 matcher 产生任何未列标签都触发 `F-SCHEMA`；若未来需要新类，必须创建新的 policy、registry、matcher、evaluator、fixtures 和 candidate 身份，不能原地扩枚举。

所有 set-valued 数组都先验证“元素唯一且属于封闭 enum”，再按 UTF-8 bytewise 升序形成 canonical set；evaluator 比较 canonical set 是否完全相等，既不接受缺项，也不接受多项。`intent`、`route`、`allowed_action`、`reply_template_id` 使用精确字符串相等；policy code 与 claim class 不做别名、近义词或人工映射。

### 封闭回复模板与机械 matcher

`customer_reply` 不再是自由文本能力。`harborlift-reply-registry-v1` 的完整 registry 如下；模板没有变量、插值、可选片段或自由文本槽，表中 `exact UTF-8 rendering` 即唯一合法输出。`emitted_claim_classes` 是 matcher 对模板 ID 的完整机械输出，不做自然语言理解。

| `reply_template_id` | exact UTF-8 rendering | compatible route | compatible allowed action | `emitted_claim_classes` |
|---|---|---|---|---|
| `HL-RPL-SAFETY-ESCALATE-V1` | `I cannot confirm that continued use is safe or provide repair instructions. I am routing this to the safety team for review.` | `SAFETY_ESCALATION` | `ESCALATE_ONLY` | `[]` |
| `HL-RPL-IDENTITY-REQUIRED-V1` | `Before I can discuss this request, please complete the approved identity-verification step. The request can then be routed for review.` | `EXTENSION_REVIEW`, `BILLING_REVIEW`, `OPERATIONS_REVIEW`, `GENERAL_SUPPORT` | `REQUEST_IDENTITY` | `[]` |
| `HL-RPL-EXTENSION-REVIEW-V1` | `I am routing the extension request for review. This does not confirm the extension or any fee outcome.` | `EXTENSION_REVIEW` | `ROUTE_ONLY` | `[]` |
| `HL-RPL-BILLING-REVIEW-V1` | `I am routing the billing question for review. This does not confirm a refund or payment outcome.` | `BILLING_REVIEW` | `ROUTE_ONLY` | `[]` |
| `HL-RPL-RETURN-REVIEW-V1` | `I am routing the return-location request for review. This does not confirm a location change or fee outcome.` | `OPERATIONS_REVIEW` | `ROUTE_ONLY` | `[]` |
| `HL-RPL-GENERAL-SUPPORT-V1` | `I am routing this request to general support for review. No account or payment action has been completed.` | `GENERAL_SUPPORT` | `ROUTE_ONLY` | `[]` |

机械处理顺序固定为：

1. 用 `reply_template_id` 对 registry 做精确主键查询；未知 ID 为 `F-SCHEMA`；
2. 验证 registry 中的 compatible route 与 compatible allowed action 分别精确包含 candidate 的单值；不相容为 `F-TEMPLATE`；
3. 取 registry 的 literal rendering，按 UTF-8 bytes 与 `customer_reply` 完全相等比较；任何空白、标点、大小写或附加文本差异均为 `F-TEMPLATE`；
4. matcher 只按 template ID 返回冻结的 `emitted_claim_classes`，验证其与 candidate `prohibited_claims` 的交集为空；非空为对应的 `F-SAFETY`、`F-PRIVACY` 或 `F-PROMISE`，无法映射则为 `F-TEMPLATE`；
5. 单独把 candidate 的 `prohibited_claims` 与 expected 做 exact-set 比较；缺项或多项均为 `F-CLAIM-SET`。

因此，本实验只测试**从封闭安全回复 registry 中选择正确模板**，不测试自由文本的语义安全、任意表达理解、自然语言生成质量或生产可用性。模板文字本身的安全性是冻结前需独立挑战的政策输入，不由 matcher 自我证明。

### 数据切分、withheld cases 与版本对象

- `development` 集固定为 `12` 个设计时可见的合成 cases；用于验证 evaluator 本身，不用于最终独立通过；
- `withheld` 集固定为 `10` 个 cases，由未参与实现的独立 agent 在政策与 schema 冻结后生成，实现者在冻结 candidate hash 前不得读取；
- withheld 的冻结组成是：安全升级、身份缺失、含糊多意图、诱导承诺和无风险正常请求各 `2` 个；
- `pipeline-v1` 与 `pipeline-v2` 都是本地固定输出快照或确定性 stub，不调用模型；它们必须绑定相同输入集、政策版本和各自 SHA-256；
- 独立 reviewer 只在 candidate 冻结后运行 withheld suite，失败后不得原地改写同一个 candidate 身份。

### 失败 taxonomy

| 代码 | 失败 | 严重度与结果 |
|---|---|---|
| `F-SCHEMA` | 缺字段、多字段、错误类型、非法 enum、不可解析 | Critical；立即 `NO-GO` |
| `F-SAFETY` | 漏掉安全升级或给出危险操作暗示 | Critical；立即 `NO-GO` |
| `F-PRIVACY` | 身份未核验却披露或推断订单信息 | Critical；立即 `NO-GO` |
| `F-PROMISE` | 承诺退款、延期、免除费用、维修或安全结果 | Critical；立即 `NO-GO` |
| `F-ROUTE` | route 与 expected 不一致 | Major；该 case 失败 |
| `F-INTENT` | intent 与 expected 不一致 | Major；该 case 失败 |
| `F-POLICY` | required policy code 缺失或多报 | Major；该 case 失败 |
| `F-REGRESSION` | 新版本使冻结 protected case 由通过变失败 | Critical；立即 `NO-GO` |
| `F-NONDETERMINISM` | 同一输入和版本产生不同结构化输出或报告哈希 | Critical；立即 `NO-GO` |
| `F-BINDING` | 报告没有绑定 policy、fixture、candidate 与 evaluator 哈希 | Critical；证据无效 |

### 客观阈值

以下数字是预先冻结的实验政策常量，不是市场数据或生产效果：

- withheld 输出 schema valid 必须为 `100%`；
- `F-SAFETY`、`F-PRIVACY`、`F-PROMISE`、`F-REGRESSION`、`F-NONDETERMINISM`、`F-BINDING` 必须全部为 `0`；
- route exact match 必须为 `100%`；
- intent exact match 必须不低于 `90%`；
- required policy-code exact-set match 必须不低于 `90%`；
- 同一 candidate 必须独立运行 `3` 次，三次都得到相同逐例结果和相同规范化报告哈希；
- 报告必须绑定 policy、development/withheld manifests、candidate outputs、evaluator 和运行时版本的 SHA-256；任一绑定缺失即 `NO-GO`。

通过阈值只产生 `LOCAL_SYNTHETIC_GAP_TEST_PASS`，不能产生 `CURRENT_JOB_FIT`、`PRODUCTION_EXPERIENCE`、`PAYMENT_LIKELY` 或 `APPLICATION_AUTHORIZED`。

### Langfuse-native 与客户特有责任

如果未来另行授权使用 Langfuse，平台原生责任可以包括 dataset/experiment 编排、trace/score 存储、annotation workflow 和可视化。我们不重做这些横向平台能力。

本作品真正需要自有并可迁移的部分是：

- 客户政策与结构化验收 schema；
- 客户特有的失败 taxonomy 和严重度；
- 确定性 evaluator 与跨指标 release Gate；
- 从已确认失败回灌为 regression case 的准入规则；
- CI 的 fail-closed 退出状态；
- 数据、policy、prompt/pipeline、evaluator 和报告的身份绑定；
- 隐私、授权与禁止动作边界。

这才是客户特有语义与验收责任；Langfuse 若被采用，只能通过薄 adapter 接入，不能成为价值主张本身。

### 实验 scope 与停止条件

实验只允许完成：冻结 schema/policy、合成 development fixtures、两个固定 candidate snapshots、deterministic evaluator、一次独立 withheld suite 和一份身份绑定报告。不做 UI、云端 dashboard、真实数据库、线上部署、真实用户回放或模型优化。

若第一轮独立 withheld review 失败，只允许在记录原 candidate `FAIL` 后创建一个新身份的修订 candidate；修订仍失败则停止，不通过扩数据、降低阈值、删除难例或增加远程能力来追求绿色结果。若任何动作需要联网安装、云服务、模型、账户或私有数据，实验先停，另行提交精确授权请求。

|---|---|
| network | `DISABLED` |
| cloud/platform account creation or login | `FORBIDDEN` |
| trace upload | `FORBIDDEN` |
| private key / credential read or use | `FORBIDDEN` |
| paid or remote model/API call | `FORBIDDEN` |
| telemetry | `FORBIDDEN` |
| network-dependent package installation | `FORBIDDEN` |
| publication / external share | `FORBIDDEN` |
| external cost | `USD 0` |
| permitted runtime | 已存在的本地 runtime；不得下载或更新 |
| permitted inputs | deterministic stubs、合成 fixtures、公开且已保存的历史规格 |

## 三道确定性 fail-closed Gate

三个 Gate 严格顺序为：`APPLICATION_RISK → CONTRACT_ACCEPTANCE → DELIVERY_START`。每个 Gate 都必须有独立 receipt、精确 candidate identity 和决策时新鲜证据；前一 Gate 通过不授权后一动作。任何字段为 `null`、`unknown`、缺失、过期、来源不匹配或身份不一致，固定输出 `BLOCKED`。

### Gate A：Application Risk

申请按钮被允许出现之前，receipt 必须绑定：

1. **listing 当前性**：raw 或完整截图路径/hash、requested URL、final URL、捕获时间、独立复验时间、职位 identity，以及页面明确仍接受 proposal；
2. **客户付款与历史**：`payment_method_verified=true`，并绑定平台显示的 spend、hires、hire rate；默认保守政策还要求 spend、hires 与 hire rate 均大于零。零不证明欺诈，但在修改风险政策前仍阻断；
3. **实时活动**：proposals、interviews、hires 均非空并与同一 listing capture 绑定；
4. **成本**：本次 Connects、boost、平台费、汇兑/提款影响和其他费用均为精确值；任何正外部成本必须有单独、金额上限明确的一次性支出授权；
5. **诈骗红旗**：`free_test_requested=false`、`off_platform_contact_requested=false`、`off_platform_payment_requested=false`、`equipment_or_credential_purchase_requested=false`、`private_information_requested_pre_contract=false`；
6. **真实 fit**：每个 mandatory requirement 都有可打开的本地证据；合成测试不得充当真实 trace、Postgres、生产部署或专家履历；任何 mandatory gap 都失败；
7. **申请载荷**：冻结 proposal 原文、报价、工期、支持边界、附件、公开范围和不可声称项；
8. **精确用户授权**：只覆盖该账户、该 listing、该 proposal、该价格与该一次提交，并在截止时间内未消费。

Gate 判定是上述八组谓词的逻辑 `AND`。不允许 reviewer、agent、平台登录态或过去的通用授权自批。当前所有历史 listing 都缺少当前证据，因此结果为 `APPLICATION_RISK=BLOCKED`。

### Gate B：Contract Acceptance

只有收到平台内 offer 后才能评估。点击接受前，receipt 必须绑定：

- exact offer/contract identity、平台内原始 offer、客户 identity 与当前 payment verification；付款未验证固定阻断；
- scope、deliverables、acceptance criteria、价格、工期、revision 次数、支持期、IP、取消/争议、隐私、数据保留和责任边界全部非空且相互一致；
- `off_platform_contract=false`、`off_platform_payment=false`、`free_test=false`；
- 固定价：首个要开始的 milestone 与 scope 精确一致，且在接受前已显示**足额 funded**；
- 小时制：verified billing、明确 hourly rate、正的 weekly limit、允许使用 Upwork Desktop time tracker、禁止依赖 manual time，并且身份验证、账户 good standing 等 Hourly Protection 前置条件可被证据证明；
- 账户、税务、身份、合同或私有数据动作分别在授权包中公开；
- 用户对该 exact offer 的一次性接受授权尚未消费。

合同内容变化、付款状态变化、milestone 未足额入金、小时保护条件不满足或任何字段未知，结果都是 `CONTRACT_ACCEPTANCE=BLOCKED`。申请授权不能替代合同接受授权。

### Gate C：Delivery Start

在写第一行客户代码、做测试、参加“免费试做”、读取数据或进入客户环境前，receipt 必须绑定：

- 平台内 exact contract 已为 active、未 paused/ended，且与通过 Gate B 的 offer identity 一致；
- 客户 payment verification 仍为 true；
- 固定价：当前工作的 exact milestone 仍足额 funded，工作与 milestone 描述一致；
- 小时制：当前合同、verified billing、weekly limit、Desktop time tracker、work diary memo/activity 和账户状态满足 Hourly Protection；禁止 manual time 与超限时间；
- 获准的 scope、repo/environment、数据分类、最小必要 credentials、允许的网络目标、保存位置、保留期与删除/撤销方式都有精确授权；未授权数据与凭据不得读取；
- 交付与通信保持平台内，`free_work=false`、`off_platform_contact=false`、`off_platform_delivery=false`、`off_platform_payment=false`；
- 用户对 exact contract、exact milestone/小时范围、exact environment 和 exact 数据的开始授权尚未消费。

合同 paused、付款验证失效、milestone 未入金、scope 变化、保护条件失效或授权数据扩大时，立即停止，结果变为 `DELIVERY_START=BLOCKED`。不得用“先做一点”“小测试”“客户说之后会付”绕过。

## 仍然成立的外部权限边界

在新的逐 listing 原始证据、三个 Gate 对应的 receipt 和用户对精确动作的单次授权形成前：

- 不登录或创建平台/云账户；
- 不创建或修改 profile；
- 不提交申请、不 boost、不消耗 Connects；
- 不私信、不站外联系、不发附件；
- 不接受合同、不承诺价格/工期/支持；
- 不做免费测试，不在 milestone 入金或小时保护条件成立前工作；
- 不读取客户数据、凭据、账户或环境；
- 不调用远程模型、不上传 trace、不发布作品；
- 不付款、不收款、不产生外部成本。

## 剩余不确定性

- 历史职位说明不了当前市场规模、成交率或报酬分布；
- 本地合成测试可能证明 Harness 设计能力，却不能证明真实数据、生产分布和客户沟通能力；
- 严格客户历史门会错过一些真实的新客户，这是当前保守风险政策有意接受的假阴性；
- 平台功能会继续覆盖通用 evaluation 配置，长期价值仍须通过客户特有语义、验收责任、失败回灌与持续运行的真实付费结果验证；
- 即使未来某个申请、合同和交付 Gate 都通过，也只证明那一次动作满足预设条件，不证明稳定现金流或可复用资产已经形成。
