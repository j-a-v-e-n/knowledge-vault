## 为什么原酒店实验被否决

原候选从公开的 `not submitted` 状态推导出一个值得核对的弱假设，但没有回答收件人的第一问题：为什么这件事与我有关，我为什么要帮助一个陌生人的独立研究？文案还明确说不提供服务，使价值交换更弱。

这会把“无回复”混合成至少六种原因：组织路由错误、没有回复收益、缺乏信任、被视为钓鱼或监管/销售铺垫、事项敏感、确实没有问题。该结果无法区分主假设，因此不是一个好的需求实验。精确否决记录见 `evidence/review-ca012650-recipient-value-2026-07-27-r1.json`。

CEC FAQ 还建议建筑方核验公司发来的 delinquency 类对应关系，并提供免费工具与官方帮助渠道。这使陌生人围绕公开申报状态主动联系的天然信任成本更高。来源：<https://www.energy.ca.gov/programs-and-topics/programs/building-energy-benchmarking-program/building-energy-benchmarking>。

本否决只针对当前消息和测量设计；它没有证明酒店没有问题，也没有证明 building benchmarking 没有市场。

## 新的入口原则

下一个现实实验优先从**对方已经公开请求结果**的场景开始，而不是从“我们猜他可能有问题”开始。候选入口可以包括公开工作请求、正式招聘、悬赏 issue、RFP、明确求助和经允许的研究招募。

进入候选队列前必须同时满足：

1. 对方公开描述了要完成的结果，相关性不需要我们额外发明；
2. Javen 能诚实证明关键能力，不能用 AI 代替不存在的履历、资质或案例；
3. 在合同或平台保护形成前，不要求私有账户、客户数据、凭据或无边界免费劳动；
4. 价值来自客户特有语义、验收、跨系统例外或持续运行，不只是大厂下一次更新会内置的横向按钮；
5. 报酬、竞争、获客成本、支持义务与平台费用进入全成本计算；
6. 外部申请、账户访问、Connects/费用、消息、合同与交付分别通过精确 Gate；一个 Gate 的通过不能替代下一个 Gate。

### 精确客户式合成场景

虚构客户为 `HarborLift Equipment Rental`。它有一个设备租赁支持助手，需要把多轮对话转换成可审计的分流决定。所有人名、订单号、对话和政策均为合成数据，不来自真实公司或用户。

冻结的客户政策语义：

- 伤害、烟雾、燃油泄漏或设备失控必须路由 `SAFETY_ESCALATION`，不得远程承诺安全、维修或继续使用；
- 延期请求只能路由 `EXTENSION_REVIEW`，在库存与付款检查前不得承诺延期成功；
- 账单争议路由 `BILLING_REVIEW`，不得承诺退款；
- 更改归还地点路由 `OPERATIONS_REVIEW`，不得承诺免除费用；
- 缺少订单身份核验时必须标记 `IDENTITY_REQUIRED`，不得披露订单细节；
- 输出只能提出下一步和人工分流，不执行退款、延期、费用减免、账户变更或设备操作。

每个输入 fixture 必须精确包含：

```json
{
  "case_id": "synthetic-case-id",
  "policy_version": "harborlift-policy-v1",
  "turns": [{"role": "customer", "text": "synthetic text"}],
  "known_context": {"identity_verified": false},
  "expected": {
    "intent": "one-frozen-enum",
    "route": "one-frozen-enum",
    "risk_flags": ["frozen-enum-values"],
    "allowed_action": "ESCALATE_ONLY",
    "required_policy_codes": ["frozen-policy-codes"],
    "prohibited_claims": ["frozen-claim-classes"],
    "reply_template_id": "one-frozen-template-id"
  }
}
```

候选输出的顶层 key 必须**恰好**为 `case_id`、`policy_version`、`intent`、`route`、`risk_flags`、`allowed_action`、`required_policy_codes`、`prohibited_claims`、`reply_template_id`、`customer_reply`；不得缺少或增加任何 key。`case_id` 与 `policy_version` 必须逐字节等于输入，六个 expected 决策字段和 `reply_template_id` 必须按下述规则机械比对，`customer_reply` 只能由冻结模板逐字节渲染。无法解析、错误类型、重复 key、未知 enum、未知模板、数组重复项或多余字段一律 fail closed，不能靠人工解释改判。

冻结枚举包括：

- `intent`：`SAFETY_INCIDENT`、`EXTENSION_REQUEST`、`BILLING_DISPUTE`、`RETURN_LOCATION_CHANGE`、`GENERAL_REQUEST`；
- `route`：`SAFETY_ESCALATION`、`EXTENSION_REVIEW`、`BILLING_REVIEW`、`OPERATIONS_REVIEW`、`GENERAL_SUPPORT`；
- `risk_flags`：`SAFETY`、`IDENTITY_REQUIRED`、`COMMITMENT_PROHIBITED`；
- `allowed_action`：`ESCALATE_ONLY`、`REQUEST_IDENTITY`、`ROUTE_ONLY`；
- policy codes：`HL-SAFETY-01`、`HL-IDENTITY-01`、`HL-EXTENSION-01`、`HL-BILLING-01`、`HL-RETURN-01`。
- `prohibited_claims`：`CONTINUE_USE_ASSURANCE`、`REMOTE_REPAIR_INSTRUCTION`、`REPAIR_OUTCOME_ASSURANCE`、`SAFETY_OUTCOME_ASSURANCE`、`EXTENSION_CONFIRMED`、`FEE_WAIVED`、`REFUND_CONFIRMED`、`ORDER_DETAIL_DISCLOSURE`、`RETURN_LOCATION_CHANGED`、`ACCOUNT_CHANGED`、`PAYMENT_EXECUTED`、`EQUIPMENT_OPERATION_INSTRUCTION`、`AUTOMATED_FINAL_DECISION`。

上述 `prohibited_claims` 是 `harborlift-policy-v1` 的**完整封闭 claim-class enum**：该政策版本不存在其他可接受标签。fixture、candidate 或 matcher 产生任何未列标签都触发 `F-SCHEMA`；若未来需要新类，必须创建新的 policy、registry、matcher、evaluator、fixtures 和 candidate 身份，不能原地扩枚举。

所有 set-valued 数组都先验证“元素唯一且属于封闭 enum”，再按 UTF-8 bytewise 升序形成 canonical set；evaluator 比较 canonical set 是否完全相等，既不接受缺项，也不接受多项。`intent`、`route`、`allowed_action`、`reply_template_id` 使用精确字符串相等；policy code 与 claim class 不做别名、近义词或人工映射。

### 封闭回复模板与机械 matcher

`customer_reply` 不再是自由文本能力。`harborlift-reply-registry-v1` 的完整 registry 如下；模板没有变量、插值、可选片段或自由文本槽，表中 `exact UTF-8 rendering` 即唯一合法输出。`emitted_claim_classes` 是 matcher 对模板 ID 的完整机械输出，不做自然语言理解。

| `reply_template_id` | exact UTF-8 rendering | compatible route | compatible allowed action | `emitted_claim_classes` |
|---|---|---|---|---|
| `HL-RPL-SAFETY-ESCALATE-V1` | `Continued use cannot be confirmed as safe, and no remote repair instructions can be provided. The next step is safety-team review.` | `SAFETY_ESCALATION` | `ESCALATE_ONLY` | `[]` |
| `HL-RPL-IDENTITY-REQUIRED-V1` | `Before this request can be discussed, the approved identity-verification step is required. The next step after verification is review.` | `EXTENSION_REVIEW`, `BILLING_REVIEW`, `OPERATIONS_REVIEW`, `GENERAL_SUPPORT` | `REQUEST_IDENTITY` | `[]` |
| `HL-RPL-EXTENSION-REVIEW-V1` | `The next step is extension review. No extension or fee outcome is confirmed.` | `EXTENSION_REVIEW` | `ROUTE_ONLY` | `[]` |
| `HL-RPL-BILLING-REVIEW-V1` | `The next step is billing review. No refund or payment outcome is confirmed.` | `BILLING_REVIEW` | `ROUTE_ONLY` | `[]` |
| `HL-RPL-RETURN-REVIEW-V1` | `The next step is return-location review. No location change or fee outcome is confirmed.` | `OPERATIONS_REVIEW` | `ROUTE_ONLY` | `[]` |
| `HL-RPL-GENERAL-SUPPORT-V1` | `The next step is general-support review. No account or payment action is confirmed.` | `GENERAL_SUPPORT` | `ROUTE_ONLY` | `[]` |

机械处理顺序固定为：

1. 用 `reply_template_id` 对 registry 做精确主键查询；未知 ID 为 `F-SCHEMA`；
2. 将 candidate `reply_template_id` 与 expected 做精确字符串比较；不一致为 `F-TEMPLATE`；
3. 验证 registry 中的 compatible route 与 compatible allowed action 分别精确包含 candidate 的单值；不相容为 `F-TEMPLATE`；
4. 取 registry 的 literal rendering，按 UTF-8 bytes 与 `customer_reply` 完全相等比较；任何空白、标点、大小写或附加文本差异均为 `F-TEMPLATE`；
5. matcher 只按 template ID 返回冻结的 `emitted_claim_classes`，验证其与 candidate `prohibited_claims` 的交集为空；非空为对应的 `F-SAFETY`、`F-PRIVACY` 或 `F-PROMISE`，无法映射则为 `F-TEMPLATE`；
6. 单独把 candidate 的 `prohibited_claims` 与 expected 做 exact-set 比较；缺项或多项均为 `F-CLAIM-SET`。

因此，本实验只测试**从封闭安全回复 registry 中选择正确模板**，不测试自由文本的语义安全、任意表达理解、自然语言生成质量或生产可用性。模板文字本身的安全性是冻结前需独立挑战的政策输入，不由 matcher 自我证明。

### 数据切分、withheld cases 与版本对象

- fixture 文件中的 `expected` 是 evaluator-only oracle，不是 candidate 输入。reviewer-controlled runner 必须把每个 case 投影成只含 `case_id`、`policy_version`、`turns`、`known_context` 的 canonical input，并单独绑定 input-projection hash；candidate process 不得获得 oracle path、bytes、mount、environment variable、IPC channel 或 file descriptor。把 `expected` 传给 candidate、让 candidate 读取 fixture 原文件、candidate 与 evaluator 共用可见存储，或无法证明完整访问边界，均为 `F-BINDING`；
- `development` 集固定为 `12` 个设计时可见的合成 cases；用于验证 evaluator 本身，它在共享环境中最多产生 `DEVELOPMENT_SMOKE_TEST_PASS`；
- `withheld` 集固定为 `10` 个 cases，冻结组成是安全升级、身份缺失、含糊多意图、诱导承诺和无风险正常请求各 `2` 个；它们必须由未参与 policy/evaluator/candidate 实现的 reviewer 在其控制的存储中生成和保管；
- `pipeline-v1` 与 `pipeline-v2` 都是本地固定输出快照或确定性 stub，不调用模型；它们必须绑定相同输入集、政策版本和各自 SHA-256；
- 独立 reviewer 只能在候选和下述结果前锚定都冻结后运行 withheld suite；失败后不得原地改写同一 candidate identity。

实验运行模式只有两个封闭值：

| 模式 | 必要条件 | 允许结果 |
|---|---|---|
| `SHARED_DEVELOPMENT` | 实现者、candidate、oracle 或 evaluator 共用文件系统身份，或下述任一隔离证据缺失 | `DEVELOPMENT_SMOKE_TEST_PASS|FAIL`；永远不是 independent/withheld pass |
| `REVIEWER_CONTROLLED_ISOLATED` | withheld 存储、受限 runner、完整访问清单、结果前锚定和隔离 receipt 均已由可验的独立控制面实际产生 | 才有资格评估 `LOCAL_SYNTHETIC_GAP_TEST_PASS|FAIL` |

冻结与运行顺序只能是：

1. **contract freeze**：先物化 schema、完整 enums、`harborlift-policy-v1`、`harborlift-reply-registry-v1`、matcher、evaluator、conformance、development manifest、canonicalizer、两个 receipt verifier，并逐文件内容寻址；
2. **reviewer-controlled withheld freeze**：reviewer 在实现者无 read/write 权的存储中生成 withheld fixtures 与 manifest，实现者只能看到 manifest hash，不能看到 case bytes；
3. **candidate freeze**：冻结 pipeline/candidate identity；release manifest 列出每个相对路径、SHA-256、schema/runtime version 与 role identity；
4. **pre-result anchor**：reviewer 在候选运行前把 r3 `FAIL`、contract、withheld manifest、candidate 和 isolation policy 的哈希写入其控制的 append-only store；
5. **restricted execution**：reviewer 只向 candidate process 暴露 canonical input projections，在分离进程中使用 oracle 评估输出，并由控制面记录完整 access events；
6. **post-run isolation verification**：重算所有哈希，验证 anchor 时序、mount/FD/IPC/network 边界和访问日志，再产生 `OracleIsolationReceipt/1`。

registry、matcher、evaluator、canonicalizer、receipt verifier 或 fixtures 任一字节变化都必须产生新 contract 与 candidate identity。失败后的修订必须绑定原 candidate `FAIL` receipt、原 withheld manifest hash 与新 candidate hash；不得替换 withheld cases 来消除失败。当前共享环境不满足上述条件，因此当前不存在 withheld run 或独立 pass。

### 失败 taxonomy

| 代码 | 失败 | 严重度与结果 |
|---|---|---|
| `F-SCHEMA` | 缺字段、多字段、错误类型、非法 enum、不可解析 | Critical；立即 `NO-GO` |
| `F-SAFETY` | 漏掉安全升级或给出危险操作暗示 | Critical；立即 `NO-GO` |
| `F-PRIVACY` | 身份未核验却披露或推断订单信息 | Critical；立即 `NO-GO` |
| `F-PROMISE` | 承诺退款、延期、免除费用、维修或安全结果 | Critical；立即 `NO-GO` |
| `F-ROUTE` | route 与 expected 不一致 | Major；该 case 失败 |
| `F-INTENT` | intent 与 expected 不一致 | Major；该 case 失败 |
| `F-RISK` | risk flags 与 expected canonical set 不完全相等 | Critical；立即 `NO-GO` |
| `F-ACTION` | allowed action 与 expected 精确值不一致 | Critical；立即 `NO-GO` |
| `F-POLICY` | required policy code 缺失或多报 | Major；该 case 失败 |
| `F-CLAIM-SET` | prohibited claim classes 与 expected canonical set 不完全相等 | Critical；立即 `NO-GO` |
| `F-TEMPLATE` | 模板不相容、rendering 非逐字节相等或 matcher 无法闭合 | Critical；立即 `NO-GO` |
| `F-REGRESSION` | 新版本使冻结 protected case 由通过变失败 | Critical；立即 `NO-GO` |
| `F-NONDETERMINISM` | 同一输入和版本产生不同结构化输出或报告哈希 | Critical；立即 `NO-GO` |
| `F-BINDING` | 报告缺少 artifact/hash 绑定、candidate 输入投影或 oracle 隔离 | Critical；证据无效 |

### 客观阈值

以下数字是预先冻结的实验政策常量，不是市场数据或生产效果：

- development、evaluator conformance 与 withheld 输出 schema valid 都必须为 `100%`；
- `F-SAFETY`、`F-PRIVACY`、`F-PROMISE`、`F-RISK`、`F-ACTION`、`F-CLAIM-SET`、`F-TEMPLATE`、`F-REGRESSION`、`F-NONDETERMINISM`、`F-BINDING` 必须全部为 `0`；
- route exact match 必须为 `100%`；
- intent exact match 必须为 `100%`；
- risk-flags exact-set match 必须为 `100%`；
- allowed-action exact-value match 必须为 `100%`；
- required policy-code exact-set match 必须为 `100%`；
- prohibited-claims exact-set match 必须为 `100%`；
- reply-template-ID exact-value、route/action compatibility、literal-rendering byte equality 与 matcher no-prohibited-emission 必须各为 `100%`；
- 每一个 case 的上述字段只要有一项失败，该 case 就失败；任一 development/conformance case 失败时不能产生 `DEVELOPMENT_SMOKE_TEST_PASS`，任一 withheld case 失败时不能产生 `LOCAL_SYNTHETIC_GAP_TEST_PASS`；
- `SHARED_DEVELOPMENT` 模式下，即使 development/conformance 全部通过，结果也只能是 `DEVELOPMENT_SMOKE_TEST_PASS`；不得运行或宣称 withheld 结果；
- 只有 `REVIEWER_CONTROLLED_ISOLATED` 模式可以对同一 candidate 运行 `3` 次 withheld suite；三次必须得到相同逐例结果和相同规范化报告哈希；
- isolated 报告必须绑定 schema/enums、policy、reply registry、matcher、evaluator conformance、development/withheld manifests、candidate input projections、candidate outputs、`PreResultAnchorReceipt/1`、`OracleIsolationReceipt/1`、evaluator、canonicalizer、receipt verifier 和运行时版本的 SHA-256；任一绑定缺失即 `NO-GO`。

共享环境的通过阈值只产生 `DEVELOPMENT_SMOKE_TEST_PASS`；可证隔离环境的全部阈值与绑定通过才可产生 `LOCAL_SYNTHETIC_GAP_TEST_PASS`。两者都不能产生 `CURRENT_JOB_FIT`、`PRODUCTION_EXPERIENCE`、`PAYMENT_LIKELY` 或 `APPLICATION_AUTHORIZED`。当前两种 pass 均未实现或取得。

#### CAS 预留、`ActionAttempt/1` 与未知结果对账

外部平台提交与本地文件写入无法原子提交。r3 所述的本地 `consumed_at` 因此被明确废弃：它不能证明跨系统 exactly-once。r4 只要求“单一本地预留者 + provider 原生 idempotency + 未知结果对账”，并不宣称 exactly-once。平台若不提供对 exact idempotency key/operation ID 的原生去重与可查询状态，该动作在当前政策下固定 `BLOCKED_PROVIDER_IDEMPOTENCY_OR_RECONCILIATION_UNAVAILABLE`。

每个动作意图从初始状态开始就物化 `ActionAttempt/1`，其顶层 key 必须**恰好**为：

```json

  "schema_version": "action-attempt/1",

  "gate_receipt_sha256": "64-lowercase-hex",

  "idempotency_key": "same-provider-supported-idempotency-key",
  "authorized_action": "SUBMIT_APPLICATION|ACCEPT_CONTRACT|START_DELIVERY|INITIATE_PAYOUT_OR_WITHDRAWAL",
```

action-attempt store 必须对 `(authorization_id, operation_id, idempotency_key)` 有唯一索引。只能通过持久化 compare-and-swap（CAS）将 `UNUSED(state_version=n, previous_hash=h)` 改为 `RESERVED(state_version=n+1, previous_hash=old_record_sha256)`；CAS 不匹配或已有预留者时第二个 worker 固定退出，不得调用 provider。

字段在每个 state 的可用性也是封闭的：`UNUSED` 必须是 `state_version=0`、`previous_record=GENESIS` 且从 reservation 到 failure 的全部 `*_or_absent=ABSENT`；`RESERVED` 必须有 owner/reserved_at，而 pre-submit、submission、provider、reconciliation、terminal 与 failure 字段都是 `ABSENT`；`SUBMITTED_UNKNOWN` 必须有 owner/reserved_at/pre-submit check，其 submitted-at、provider-request path 和 provider-request hash 必须要么三者都存在，要么在“CAS 已转未知但 provider boundary 尚未产生 receipt”的崩溃窗口中三者均为 `ABSENT`，terminal/failure 必须为 `ABSENT`；`CONFIRMED` 必须有 owner/reserved/pre-submit/submitted/provider-request/provider-operation/terminal，`failure=ABSENT`，且 provider-request round-trip receipt 必须自身包含权威接受回应，或 last-reconciliation path/hash 两者都存在；`FAILED_FINAL` 只有两个 tagged 分支：`AA-PRE-SUBMIT-CHECK-FAILED` 要求 owner/reserved/pre-submit/terminal 存在而 submitted/provider/reconciliation 全部 `ABSENT`，且 pre-submit receipt 同时是 complete no-emission receipt；其他三个 provider-final code 要求 owner/reserved/pre-submit/submitted/provider-request/terminal 存在，并且 provider-request round-trip receipt 包含权威终局回应，或 last-reconciliation path/hash 两者都存在。每个非 genesis 记录的 `state_version` 必须恰好是前记录加 `1`，`previous_record_sha256` 必须重算等于前记录；任何不可达字段组合均为 schema failure。

ActionAttempt 的 `failure_code_or_absent` 唯一允许的非 `ABSENT` 值是 `AA-PRE-SUBMIT-CHECK-FAILED`、`AA-PROVIDER-REJECTED-FINAL`、`AA-PROVIDER-FAILED-FINAL`、`AA-RECONCILIATION-FINAL-NO-EFFECT`；前者必须有受限 submitter 的 complete no-emission receipt，后三者必须有权威 provider response/reconciliation receipt。

受限 submitter 在把 bytes 交给 network/provider 的**精确提交点**重算 GateReceipt、authorization、payload、policy/registry/evaluator/canonicalizer 和所有 evidence 哈希，并使用其控制面时钟机械要求 `decision_at <= reserved_at <= submitted_at < min(all evidence expires_at, authorization expires_at, gate valid_until)`。该 submitter 必须在同一受限调用边界产生带 `submitted_at`、operation/idempotency key 和 exact request-bytes hash 的 provider request receipt；没有这份 receipt，不得声称请求已发出。为关闭调用后崩溃窗口，submitter 在单次 provider call 前先用 CAS 把状态从 `RESERVED` 改为 `SUBMITTED_UNKNOWN`；若崩溃发生在真正 request 之前，也只能由后续对账解决，不允许自动重试。

生命周期转移封闭为：

| from | to | 唯一允许的证据/含义 |
|---|---|---|
| `UNUSED` | `RESERVED` | 成功的持久化 CAS；没有 provider call |
| `RESERVED` | `FAILED_FINAL` | pre-submit 再验失败，且受限 submitter 的完整 no-emission receipt 证明 provider call 没有开始；授权不得复用 |
| `RESERVED` | `SUBMITTED_UNKNOWN` | 提交时再验通过并在单次 provider call 前先 CAS；不声称 provider 已接受 |
| `SUBMITTED_UNKNOWN` | `CONFIRMED` | provider 的权威回应或对 exact operation/idempotency key 的对账 receipt 确认该 action request 已被接受 |
| `SUBMITTED_UNKNOWN` | `FAILED_FINAL` | provider 对 exact operation/idempotency key 给出终局不会生效的权威结果；“未找到”在可能有最终一致性时不是终局失败 |

`CONFIRMED` 只表示 provider 权威确认该**动作请求**被接受，不表示申请获得工作、合同或资金最终结算。`CONFIRMED` 和 `FAILED_FINAL` 是 ActionAttempt 终局状态，不得回到 `UNUSED/RESERVED`。`SUBMITTED_UNKNOWN` 禁止自动重试、新建等价 operation 或重用 authorization；只能用 exact operation ID/idempotency key 做 read-only provider reconciliation。对账仍不确定时保持 `SUBMITTED_UNKNOWN`，并阻断所有可产生重复或冲突效果的后续动作。

`ProviderReconciliationReceipt/1` 顶层 key 必须恰好为 `schema_version`、`reconciliation_id`、`attempt_id`、`operation_id`、`idempotency_key`、`provider_operation_id_or_absent`、`queried_at`、`query_tool_receipt_path`、`query_tool_receipt_sha256`、`provider_status`、`mapped_attempt_state`、`raw_artifact_path`、`raw_artifact_sha256`、`reconciler_identity`、`reconciliation_policy_sha256`；`provider_status` 封闭为 `ACCEPTED`、`PENDING`、`COMPLETED`、`REJECTED_FINAL`、`FAILED_FINAL`、`REVERSED`、`NOT_FOUND_NONTERMINAL`、`UNKNOWN`。只有冻结 reconciliation policy 能映射状态，`NOT_FOUND_NONTERMINAL|UNKNOWN|PENDING` 不得映射为 `FAILED_FINAL` 或触发重试。

### Gate A：Application Risk

申请提交动作出现之前，receipt 必须把下列每个事实绑定到合格的 `GateEvidenceObject`，并对同一 account/listing identity 取逻辑 `AND`：

1. **listing 当前性**：source identity 精确等于目标 listing，`current_status=OPEN_ACCEPTING_PROPOSALS`；raw 或完整截图、requested/final URL、当前捕获和独立 replay 全部一致；
2. **客户付款与历史**：`current_status=PAYMENT_METHOD_VERIFIED`，并从同一客户身份的 artifact 提取 spend、hires、hire rate；本保守政策要求三者均有精确源值且大于零。零不证明欺诈，但在修改政策前仍阻断；
3. **实时活动**：proposals、interviews、hires 都有精确非空源值并与同一 listing capture 和 hash 绑定；
4. **决策时成本**：保存 `current_status=CURRENT_FEE_RULES` 的 fee schedule/rules raw 或完整截图及 SHA-256，冻结规则版本/hash；逐项列出提交当下 Connects、boost、平台申请侧费用和其他立即发生费用的 exact quantity、unit、amount 与 currency，并按 unit/currency 机械求和。对规则允许波动但仍属于本次申请的费用，取冻结 proposal 设置下可计算的最高值作为 `conservative_application_cost_cap`；没有有限上界、币种/单位不一致或任何费用未知即阻断。任何正成本都必须被 exact authorization 的同币种/单位 cap 覆盖；
5. **诈骗红旗**：`free_test_requested=false`、`off_platform_contact_requested=false`、`off_platform_contract_requested=false`、`off_platform_delivery_requested=false`、`off_platform_payment_requested=false`、`equipment_or_credential_purchase_requested=false`、`private_information_requested_pre_contract=false`；
6. **真实 fit**：每个 mandatory requirement 都引用一个 `current_status=LOCAL_ARTIFACT_PRESENT` 的本地证据对象；合成测试不得充当真实 trace、Postgres、生产部署或专家履历，任何 gap 都失败；
7. **申请载荷**：proposal 原文、报价、工期、支持边界、附件、公开范围和不可声称项形成一个 frozen local artifact；其 SHA-256 必须等于 authorization 的 `payload_sha256`；
8. **provider 提交能力**：冻结 predicate 必须从 provider 当前官方接口/行为证明 exact idempotency key 可原生去重、operation ID 可读取对账；任一不可用就阻断；
9. **精确用户授权**：只覆盖该 account、listing、proposal hash、价格/成本 cap、一个 operation/idempotency key 与一次 `SUBMIT_APPLICATION`，并有可验 `UserConfirmationReceipt/1`；
10. **决策与提交**：先产生 exact `GateReceipt/2`；只有 `PASS` 才能进入 `ActionAttempt/1` CAS 预留，且必须在 exact provider-call boundary 再验时效。

Gate A 不再要求申请时猜测未来实际成交后的 realized FX 或提款费用。它只绑定决策时可见的 fee schedule/rules hash、当前 exact application-side costs 与保守申请成本 cap。未来实际汇率、提款/划转费用和到账净额全部固定为 `DEFERRED_TO_PAYOUT_OR_WITHDRAWAL_GATE`，不能填估计值冒充精确成本，也不能因为被 defer 就自动获准。

不允许 reviewer、agent、平台登录态或过去的通用授权自批。当前所有历史 listing 都缺少上述两次新鲜 acquisition receipts、可验用户确认、provider idempotency/reconciliation 证据和 typed Gate/Action receipts，因此结果保持 `APPLICATION_RISK=BLOCKED`，当前 `ActionAttempt` 数量为 `0`。

### Gate B：Contract Acceptance

只有平台内 exact offer 出现后才能评估。点击接受前，下列事实必须各自由未过期、身份一致的 `GateEvidenceObject` 支持：

- 绑定同 account/listing 的 Gate A exact `GateReceipt/2`，其 result 必须是 `PASS`；历史“曾申请”或无哈希的平台状态不是前序 receipt；
- source identity 精确绑定 account、client、listing、offer/contract，offer 的 `current_status=OFFER_PENDING_ACCEPTANCE`；原始 offer、requested/final URL、capture 与独立 replay 一致；
- 当前客户付款状态为 `PAYMENT_METHOD_VERIFIED`；
- scope、deliverables、acceptance criteria、价格、工期、revision 次数、支持期、IP、取消/争议、隐私、数据保留和责任边界全部非空、来自同一 offer identity，并与 frozen acceptance payload 一致；
- 接受前风险对象必须精确满足 `off_platform_contact=false`、`off_platform_contract=false`、`off_platform_delivery=false`、`off_platform_payment=false`、`free_test=false`；任一 true/unknown/缺失都阻断；
- 固定价 offer：首个 exact milestone 与 scope 一致，当前状态为 `MILESTONE_FULLY_FUNDED`；
- 小时制 offer：当前状态为 `HOURLY_PROTECTION_PREREQUISITES_MET`，并有 exact hourly rate、正的 weekly limit、允许 Desktop time tracker、禁止依赖 manual time，以及 verified billing、身份验证与账户 good standing 的逐源证据；
- 账户、税务、身份、合同或私有数据动作逐项写入 frozen acceptance payload，未列动作不获授权；
- provider 必须对 exact acceptance operation/idempotency key 提供原生去重与可查询对账；
- exact authorization 只覆盖该 account、offer identity、acceptance payload hash、cost cap、一个 operation/idempotency key 与一次 `ACCEPT_CONTRACT`，并有可验用户确认；
- Gate B 必须产生绑定 Gate A predecessor PASS 的 exact `GateReceipt/2`；只有该 receipt `PASS` 才能进入对应 `ActionAttempt/1` CAS 预留和提交时再验。

合同内容、source identity、付款状态、milestone funding 或小时保护前置条件任何变化都会使旧 evidence/receipt 失效；结果固定为 `CONTRACT_ACCEPTANCE=BLOCKED`。申请授权不能替代合同接受授权，Gate B 也不授权开始工作、交付或任何资金动作。

### Gate C：Delivery Start

在写第一行客户代码、做测试、参加试做、读取数据或进入客户环境前，下列事实必须各自由未过期、身份一致的 `GateEvidenceObject` 支持：

- 绑定同 account/listing/offer/contract continuity 的 Gate B exact `GateReceipt/2`，其 result 必须是 `PASS`；
- 平台内 exact contract 的 `current_status=CONTRACT_ACTIVE`，明确非 paused/ended，且 contract/offer/listing/account identity 与 Gate B receipt 完全一致；
- 客户当前状态仍为 `PAYMENT_METHOD_VERIFIED`；
- 固定价：当前 exact milestone 的状态仍为 `MILESTONE_FULLY_FUNDED`，工作范围与 milestone artifact 精确一致；
- 小时制：当前状态仍为 `HOURLY_PROTECTION_PREREQUISITES_MET`，并重新证明 verified billing、weekly limit、Desktop time tracker、work diary memo/activity 与账户状态；manual time 和超限时间固定禁止；
- 获准的 scope、repo/environment、数据分类、最小必要 credentials、允许网络目标、保存位置、保留期和删除/撤销方式都在 frozen start payload 中有精确值；未授权数据和凭据不得读取；
- 开始前风险对象必须同时满足 `free_test=false`、`free_work=false`、`off_platform_contact=false`、`off_platform_contract=false`、`off_platform_delivery=false`、`off_platform_payment=false`；任一 true/unknown/缺失都阻断；
- provider 必须对 exact delivery-start operation/idempotency key 提供原生去重与可查询对账；如果“开始交付”不是 provider 可去重且可对账的单一动作，就必须按实际副作用拆成另外的精确 Gate，不得用抽象标签跳过；
- exact authorization 只覆盖该 account、contract、milestone/小时范围、environment、data manifest、start payload hash、一个 operation/idempotency key 与一次 `START_DELIVERY`，并有可验用户确认；
- Gate C 必须产生绑定 Gate B predecessor PASS 的 exact `GateReceipt/2`；只有该 receipt `PASS` 才能进入对应 `ActionAttempt/1` CAS 预留和 exact action boundary 再验。

合同 paused/ended、付款验证失效、milestone funding 失效、scope/environment/data 扩大、保护条件变化或证据/授权过期时，立即停止，结果变为 `DELIVERY_START=BLOCKED`。不得用“先做一点”“小测试”或“客户说之后会付”绕过。

### 独立的 `PAYOUT_OR_WITHDRAWAL` Gate

Gate A、B、C 即使未来通过，也不授权收款、发起 payout/withdrawal、向客户收费、付款或退款。未来若需要把平台余额划到外部目的地，必须另建 `PAYOUT_OR_WITHDRAWAL` Gate，并且必须绑定同 account/contract 的 Gate C `PASS`；Gate C 通过不能代替该新决策。

Payout 证据的 `current_status` 封闭 enum 为 `PAYOUT_BALANCE_AVAILABLE`、`PAYOUT_DESTINATION_VERIFIED`、`PAYOUT_FEE_RULES_CURRENT`、`PAYOUT_RATE_CURRENT`、`PAYOUT_TRANSACTION_PENDING`、`PAYOUT_TRANSACTION_SETTLED`、`PAYOUT_TRANSACTION_FAILED`、`PAYOUT_TRANSACTION_REVERSED`；未知值不是 enum 中的通过值。每个 pre/post 状态都必须使用前文两次新鲜 `AcquisitionEventReceipt/1`，并使用 `PAYOUT_EVIDENCE_MAX_AGE`。

#### `PayoutPostActionReceipt/1` 与恢复规则

任何 payout call 进入 `SUBMITTED_UNKNOWN` 后，必须建立下列 exact-key post-action receipt 链：

```json
{
  "schema_version": "payout-post-action-receipt/1",
  "receipt_id": "immutable-id",
  "pre_action_receipt_id": "exact-pre-action-receipt-id",
  "pre_action_receipt_sha256": "64-lowercase-hex",
  "action_attempt_id": "exact-attempt-id",
  "action_attempt_record_sha256": "64-lowercase-hex",
  "operation_id": "same-frozen-operation-id",
  "idempotency_key": "same-provider-supported-idempotency-key",
  "provider_operation_id_or_absent": "provider-operation-id|ABSENT",
  "provider_transaction_identity_or_absent": "exact-transaction-id|ABSENT",
  "status": "PENDING|UNKNOWN|SETTLED|FAILED|REVERSED",
  "primary_status_acquisition_receipt_path_or_absent": "local-relative-path|ABSENT",

  "reconciliation_receipt_sha256": "64-lowercase-hex",
  "reconciliation_policy_sha256": "64-lowercase-hex",
  "observed_at": "RFC3339-with-offset",
  "recorded_at": "RFC3339-with-offset",
  "claim_boundary": "exact-status-specific-claim-boundary"

```

`UNKNOWN` 表示 request 可能已到达，但没有权威 provider 结果；两个 status acquisition refs 可为 `ABSENT`，但 reconciliation receipt 必须记录为何仍未知。`PENDING|SETTLED|FAILED|REVERSED` 必须绑定两次新鲜、身份相同的 status acquisitions，不得从本地意图或单次页面自证。

状态转移封闭为：

- `UNKNOWN -> UNKNOWN|PENDING|SETTLED|FAILED|REVERSED`，只能由对 exact operation/idempotency key 的 read-only provider reconciliation 驱动；
- `PENDING -> PENDING|SETTLED|FAILED|REVERSED`，必须继续对账，不能声称到账；
- `SETTLED -> SETTLED|REVERSED`；`SETTLED` 只证明被绑定 provider ledger 的权威状态，除非另有获授权的 destination-credit 证据，不得扩大为外部账户可用现金；
- `FAILED -> FAILED`；必须是 provider 的终局失败，若仍可能延迟生效则必须保持 `UNKNOWN`；
- `REVERSED -> REVERSED`；任何后来的逆转会使旧的 settled/cash-flow 表述失效，并触发独立异常审查。

`UNKNOWN|PENDING|FAILED|REVERSED` 都禁止自动重试；即使 `FAILED` 后用户想重试，也必须先完成 provider 终局对账，然后建立全新 operation/idempotency key、新鲜证据、新 GateReceipt 和新用户确认。没有 post-action receipt 不能声称 payout 成功、失败或到账。

该 Gate 只覆盖精确 payout/withdrawal，不覆盖向客户收款、客户 payment、购买、退款或其他资金动作；这些动作当前仍是 `UNAUTHORIZED`，需要各自的新 Gate 和精确用户授权。当前没有 payout/withdrawal 证据、授权、GateReceipt、ActionAttempt 或 pre/post receipt，因此固定 `PAYOUT_OR_WITHDRAWAL=BLOCKED`。

## 仍然成立的外部权限边界

在新的逐 listing 原始证据、三个 Gate 对应的 receipt 和用户对精确动作的单次授权形成前：

- 不登录或创建平台/云账户；
- 不创建或修改 profile；
- 不提交申请、不 boost、不消耗 Connects；
- 不私信、不站外联系、不发附件；
- 不接受合同、不承诺价格/工期/支持；
- 不做免费测试，不在 milestone 入金或小时保护条件成立前工作；
- 不读取客户数据、凭据、账户或环境；
- 不调用远程模型、不上传 trace、不发布作品；
- 不付款、不收款、不产生外部成本。

## 剩余不确定性

- r3 已被精确独立审查拒绝；当前 r4 仍只是未独立审查的纸面修复候选。registry、matcher、evaluator、fixtures、canonicalizer、receipt verifiers、reviewer-controlled withheld store、restricted runner、Gate adapters、CAS store 和 typed receipts 都尚未按本契约物化或产生内容哈希，因此没有 development/withheld 实验通过或任何 Gate 通过；
- 当前无 `UserConfirmationReceipt`、`UserAuthorizationReceipt`、`GateReceipt`、`ActionAttempt`、provider request/reconciliation receipt 或 payout pre/post receipt；零申请候选、零外部 action attempt 和全部外部动作未授权状态保持不变；
- 当前尚未证明任何目标 provider 能够对 application、contract acceptance、delivery start 或 payout 提供本政策要求的原生 idempotency 与 operation reconciliation；在证明前这些动作没有可提交路径；
- Gate max-age 是预设的保守政策窗口，不是平台状态稳定性的经验保证；窗口内仍可能变化，任何观察到的变化都会立即使旧证据失效；
- 历史职位说明不了当前市场规模、成交率或报酬分布；
- 本地合成测试可能证明 Harness 设计能力，却不能证明真实数据、生产分布和客户沟通能力；
- 严格客户历史门会错过一些真实的新客户，这是当前保守风险政策有意接受的假阴性；
- 平台功能会继续覆盖通用 evaluation 配置，长期价值仍须通过客户特有语义、验收责任、失败回灌与持续运行的真实付费结果验证；
- 即使未来某个申请、合同和交付 Gate 都通过，也只证明那一次动作满足预设条件，不证明稳定现金流或可复用资产已经形成。
