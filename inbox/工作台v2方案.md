# 工作台 v2 (workbench/) — 调研 + fork/adopt/build 裁定 + 分阶段架构方案

## Context（为什么做）

Dashboard v1 是只读快照（自己的 README 写明"只看不批…web 审批是 v2"）：owner 看板要开 file://、审批要手动改 vault 卡片文件、手机看不了、没有 pipeline 位置视图和历史趋势。工作台 v2 = owner 的"办公室"：一个窗口看全公司、走进任何一环看细节、页面上直接批、手机任意 WiFi 可达；Phase B 再加"秘书"聊天派工。v1 保持运行不动，直到 v2 验收。

本方案按 thorough-research-search 纪律产出：baseline 先行、EN+中文双语、载重引用全部 WebFetch 实解析、每条调研线各自跑了独立红队、双井判干。下面每个裁定都带证据链（细节见附录）。

## 一句话总裁定（fork/adopt/build）

**整库 fork 零个。自建一个薄壳（文件→read-model + 看板页 + intent 队列），借四个硬件，抄三个设计。**

| 块 | 裁定 | 方案 |
|---|---|---|
| Ring 状态渲染（卡片→pipeline 位置→gate 通过率→freshness） | **BUILD**（核心，无可替代） | 两语言搜穿：没有任何工具理解"任意本地文件业务状态"——这层正是差异化 |
| 远程访问 + 认证 | **ADOPT** | Tailscale 免费版 + `tailscale serve`，device approval 开，绝不 Funnel。$0、零公网暴露、身份=注入 header ⇒ web 层结构性无密钥 |
| Intent 队列 | **BUILD（薄）+ 复用自家机器** | 本地非同步盘一个 SQLite（WAL）当队列+审计账本，~40 行 stdlib；applier = 现有 publish_watch 模式的新 watcher |
| 会话/成本观测 | **ADOPT 官方** | `CLAUDE_CODE_ENABLE_TELEMETRY=1` 原生 OTel 白送；会话层坚决不自建（官方 Remote Control / Agent View 正面扑向这块） |
| Phase B 秘书 | **ADOPT 官方底座** | Claude Agent SDK（唯一官方程序化路径）+ 留 API-key 降级（订阅计费政策 6-15 暂停中，随时可能重启） |
| 图表 | **BUILD→可选 ADOPT** | 先手搓 inline SVG sparkline；owner 选定视觉参考后才考虑 vendored uPlot |
| 设计抄袭清单 | **STEAL 设计不 fork 库** | Backlog.md 的 frontmatter-卡片→看板；MeisnerDan mission-control 的审批流；Axiom 的 span-waterfall 当 FSM 管线视图 |
| ChatGPT Work / Codex 合并 | **IGNORE** | 8 项需求 0 实覆盖；Work 无 API；仅 remote MCP 看不见本地文件；只作秘书层 UX 参考 |
| Claude Cowork | **PARTIALLY ADOPT** | 不当 workbench 本体（req 1-5,7 结构性给不了）；借三件：Dispatch（手机→本机派工）、Remote Control（本地 Claude Code 对话多端可见）、Agent SDK |
| Langfuse/LangSmith/AgentOps/Dify/CrewAI/AutoGen Studio | **不采用** | 分别死于：六服务运维税 / Enterprise-only self-host / ELv2+结构错配 / 要求重写 rings / 企业闭源 / 官方自认非生产+弃养 |

**警世恒言（查到的）**：这个赛道 12 个月内 Omnara archived、Vibe Kanban sunsetting、opcode 停摆、Bloop 关门——平台风险是常态，薄自建最抗风险。David Dias 的教训（厚面板成笼子）解法 = 事实源留在文件，面板只做无状态投影——v1 的 structural read-only 直觉是对的，v2 只加 web/远程/审批三块。

## 架构（Phase A）

```
                手机 / Mac 浏览器（任意 WiFi）
                          │ HTTPS
                ┌─────────▼──────────┐
                │ tailscale serve     │ device approval ON；绝不 Funnel
                │ (注入 Tailscale-User-Login header)
                └─────────┬──────────┘
                          │ http://127.0.0.1:8787（仅 loopback）
   ┌──────────────────────▼───────────────────────┐
   │ 进程1: workbench/server.py（launchd 常驻）      │
   │  HTTP 路由(5 tabs) + read-model 刷新线程 + SSE  │
   │  唯一写动作 = INSERT INTO intents               │
   └───────┬──────────────────┬────────────────────┘
           │ INSERT           │ 重建（可丢弃）
   ┌───────▼────────┐  ┌──────▼──────────┐
   │ intents.sqlite  │  │ readmodel.sqlite │  都在 workbench/state/（本地盘，
   │ 只增不删=审计账本│  │ 可 rm 随时重建    │  gitignored，绝不进 Drive vault）
   └───────┬────────┘  └──────▲──────────┘
           │ claim pending→applying   │ 只读 collectors
   ┌───────▼──────────────┐  ┌────────┴──────────────────────┐
   │ 进程2: applier.py     │  │ ring 状态文件（只读）：          │
   │ (launchd 2min;        │  │ innovation runs/manifest/kill, │
   │  O_EXCL 锁; RUN_WINDOW│  │ commercial probes/events,      │
   │  期间拒动)             │  │ craft ledger, ops, v2 metrics  │
   │ 唯一对 vault 的写者：   │  └───────────────────────────────┘
   │ 把 decision/裁决 行写进 │  ┌───────────────────────────────┐
   │ 0-工作台卡片(vault_call │  │ 现有机器（一行不改）：           │
   │ +temp/rename)，然后    │──▶ publish_watch 30min fan-out 照 │
   │ launchctl kickstart   │  │ 常消费 decision 行→施加后果→     │
   └───────────────────────┘  │ 机器回执→归档→挪 done/          │
                              └───────────────────────────────┘
```

**核心决定：applier 不施加后果，只代替 owner 的手写 verdict 行**——现有四个 watcher（commercial 发/edit/跳过、craft 发+理由、supervisor 裁决-N、activation 激活）照常消费。零 ring 代码改动，机器批和人批在审计链上不可区分。已核对四个 family 的守卫（红队复核过）：不覆盖已填 decision（沿用 activate_watch.py:62-64/81 的 placeholder 判断——各 family 幂等机制并不统一：supervisor 先删 sidecar、craft 失败时保留 sidecar 以便重试、activation 根本无 sidecar——但 applier 永不碰任何 sidecar，只写卡片，所以差异不影响设计）；supervisor 卡的 N 个裁决作为一个 intent 一次交齐（watcher 要求全填才动）；写完 `launchctl kickstart` publish_watch 把 30 分钟延迟压到秒级。
**红队发现的窄竞态及对策**：现有 watcher 的 `_annotate()` 是无锁 read-modify-write，定时 tick 与 kickstart 若重叠在同一张卡上，理论上存在 lost-update（此风险今天就存在，applier 提高了触发频率）。对策：applier 写入后延迟复读校验 verdict 行仍在，丢失则重写（self-healing）；红队清单加第 ⑨ 项专测双 watcher 重叠。

**技术栈（已验证依据）**：v2/.venv 无可用的 web 框架（fastapi/flask/uvicorn 均无；aiohttp 3.14 作为 cosmic_ray 等的传递依赖存在但 repo 自身代码零引用，不作为选型基础）→ Python 3.13 stdlib `ThreadingHTTPServer` + vendored htmx 单文件 + f-string 模板（repo 现成习语）+ SSE（chunked response）。一个进程、一个 plist、零 build step、零新依赖。

**Read-model**：`rings / items(name,lane,stage,…) / item_events / cards / rollups / meta` 六张表。刷新分层：本地 ring 文件 60s（mtime 门控）；vault 卡片 5min（走 vault_call 30s 守卫）。freshness 双层诚实：source `数据截至`（v1 的 grace-hours 芯片逻辑）+ `采集于` + Drive 超时显式红标。

**Pipeline 位置视图**：`position.py` 纯折叠——manifest.jsonl 事件 ∪ killlist.jsonl（死在哪关）∪ probes/<name>.json（9 FSM 态 + history[]），按 `name` join（已核实三个面 name 一致；probe 里还内嵌完整 candidate dict）。渲染成 Axiom 式 span-waterfall，固定 lane：信号→gate→隔离区→bench/激活→triage→champion→page-live→审批→collecting→verdict→fed-back/killed。**Phase A 不新增 lineage id**（违反"不改 ring"边界，收益边际）；验收后一行 follow-up（triage 把 candidate_id 抄进 probe 顶层），历史 join 在 UI 标注"按名字匹配"。craft 独立 lane（artifact 命名域不同，不强行 join）。

**Collectors**：workbench/collectors.py 新写更丰富的版本，路径常量照 repo 教义复制不 import（dashboard/generate.py:24-27 明文；v1 的一行摘要对下钻太粗；并行运行期两个面板命运解耦）。v1 一个字节不动。

**趋势 rollups**（刷新时算，存 rollups 表，inline SVG 画）：gate 通过率（runs/*/gate/*.verdict.json）、分关卡 kill 数（killlist）、晋升/激活（manifest）、probe FSM 转移与结局（events.jsonl）、craft verdicts（ledger.jsonl）、v2 deliveries（metrics/cycle-*.json，先归一化 /home/javen/ Linux 路径）。UI 里诚实标注：趋势起点=现有日志起点（coach 历史从未落盘，就是没有）。

## 里程碑（skeleton-first）

- **M0 可点击骨架（无真数据）**：5 个 tab（总览/各环详情/钱与市场/审批/秘书占位）+ 左 tab rail + 全部区域带 `示例数据` 水印的假数据 + 管线 lane 图假条目 + CSS 变量主题槽 + Tailscale 打通。**验收**：owner 在 Mac 和手机上点通全部 tab，认可框架结构。此时给 owner 看视觉参考候选，选风格。
- **M1 read-model + 真数据**：collectors/readmodel/position/rollups/freshness 全接通；总览=环健康+计数；各环详情=下钻+FSM waterfall+per-idea 位置；钱与市场=probe 漏斗+趋势。**验收**：每个数字 UI 内可溯源到文件路径；owner 抽查 3 项（如"spendbook 在哪一格"）与原始文件一致；杀掉 server → v1 不受影响；删 readmodel.sqlite → 自愈。
- **M2 intent 队列 + 页面审批**：四个 family 的审批表单（decision + 一行理由）、intent 状态 SSE 实时、kickstart 接线、红队清单全跑。**验收（真实结果标准）**：owner 用手机批一张**真卡**：intent <1s 入列 → applier 写 verdict 行 → publish_watch 施加后果 → 卡进 done/ → 审计链完整。手改卡片的老流程同时照常可用（迁移桥）。
- **M3 远程打磨 + 加固**：选定参考的手机优先 CSS、降级徽章、安装脚本、intents.sqlite 备份注记。**验收**：owner 在非家庭 WiFi 用手机把 workbench 当主面板用满一周，宣布验收；之后才谈 v1 退役。
- **Phase B 秘书（设计冻结，M3 后建）**：`workbench/secretary/run.py` 用 claude-agent-sdk；按需启动（绝不常驻）+ 硬预算（轮数/日会话上限=低频 by construction）；系统上下文=BLUEPRINT.md 等只读；可写面只有两个：frozen briefs → v2/briefs/（现有管道消费，派工=文件投递，绝不直接调 ring）+ 草稿卡 → secretary/outbox/（owner 经同一 intent 队列晋升）；transcripts jsonl 落盘、tab 内只读渲染（对话可见）；订阅登录为主 + ANTHROPIC_API_KEY 降级路径常备（政策火山）；telemetry 开关亮成本。

## 安全清单

- 只绑 127.0.0.1:8787（启动时断言）；tailscale serve + device approval；绝不 Funnel。
- Header 信任逻辑：`Tailscale-User-Login` 可信**仅因为** socket 是 loopback（LAN 根本连不进来）；header 在场 ⇒ 必须等于钉死的 owner login 否则 403+审计行。
- workbench/ 零密钥：不读 .env / publish-creds.toml；applier 每次写跑 `assert_no_secret`（fsm.py:47 的 fail-closed 闸复制）。
- Intent 白名单校验：family × decision 语法逐 family 硬编码（发 | edit:<text> | 跳过 | craft 必须带理由 | 裁决-N 全填 | 激活）；目标卡文件名必须匹配该 family 前缀且存在；其余一律 rejected。
- CSRF：每次启动随机 token 嵌页面，POST 必带 `X-Workbench-Token` + Origin/Host 校验；无 cookie ⇒ 无可骑劫的环境凭证。
- 幂等：UUIDv7 + 唯一索引 INSERT OR IGNORE——手机卡顿双击只生效一次。
- 丢手机 = Tailscale 控制台移除设备一键了事；手机上没有任何凭证（device approval 挡住静默重入网）。

## 诚实边界（v2 不做什么）

- 不改任何 ring 逻辑；审批后果 100% 由现有 watcher 施加。
- 不自建 Claude 会话查看器（交给官方 Remote Control / Agent View；只展示 OTel 计数）。
- 趋势受限于现有日志起点；coach 历史空缺就是空缺。
- vault 写走 Drive：Drive 挂起时 intent 诚实停在 pending/applying，绝不丢，但会迟。
- 审批延迟下限 = applier 轮询 + watcher kickstart，秒级到 2 分钟，不是即时。
- 单 owner 工具，无用户管理；web 进程自身零写权限（INSERT intents 除外）。
- Tailscale Personal = 非商用条款；workbench 若变成营收基础设施需复查合规。

## 验证 + 红队清单（M2 门）

黄金路径：手机 LTE（非家庭网）→ 批真卡 → grep vault 卡片确认 verdict 行 → publish_watch 后果落地 → done/ + receipts + manifest 事件 → intent 行 applied、时间戳成链。
红队项：① 别的 LAN 设备伪造 header → 连接被拒（loopback）② 本机 curl 伪造错误 login → 403+审计 ③ 同幂等键双提交 → 一行；快速双击 → 一 applied 一 duplicate ④ RUN_WINDOW 期间投递 → pending 挂住+UI 提示，窗口关后生效 ⑤ 模拟 Drive 挂起 → vault_call 超时、intent failed(vault-timeout) 下轮重试、server 不卡、面板显式红标 ⑥ owner 先手填 decision → applier 检出已填、failed(conflict)、绝不覆盖 ⑦ kill -9 applier 中途 → 陈旧 claim 按龄回收、写前复查 placeholder 防双写 ⑧ 删 readmodel.sqlite → 自愈重建、期间显示缺数据不说谎 ⑨ 定时 tick 与 kickstart 的 publish_watch 双实例重叠于同一张卡 → applier 的写后复读校验捕获 lost-update 并重写（红队新增项）。

**最终红队记录**：fresh-context reviewer 对本方案逐条证伪（32 次工具调用，全部 repo 内部声明逐一对源码核验）：0 blocking、4 minor（aiohttp 措辞、sidecar 机制非统一、行号引用、⑨ 竞态）——全部已修入上文；8 项需求覆盖核验无一漏落；验收标准核验为真实结果制、无过程指标陷阱。
