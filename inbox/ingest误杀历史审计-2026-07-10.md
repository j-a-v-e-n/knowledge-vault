# ingest 误杀历史审计（resume 吞新候选 bug 的受害者清查）2026-07-10

背景：当日修复的 ingest resume bug——同日已有 checkpoint 时，新到候选被直接过滤并记
`ingest-filtered` 击杀（stage=commercial-triage，CK3 永久拒绝重入），**分类器从未见过它**。
本审计清查历史上是否存在这类"零分类击杀"受害者，有则解禁并重新入池。

## 扫描范围与判定标准

- 扫描对象：`innovation/killlist.jsonl` 全部 **25 条**击杀记录。
- 嫌疑类（唯一可能由 ingest 路径产生的击杀）：
  1. `stage=commercial-triage` 且 reason 以 `ingest-filtered` 开头 → 对照当周
     `innovation/commercial/runs/<week>/checkpoint-commercial-collect.json` 是否含 `cand-<name>` 记录；
  2. `stage=ingest-gate`（日常管道 ⑧→⑥ 击杀）→ 对照当周 `innovation/runs/<week>/checkpoint-gate.json`
     是否含该候选 id 记录。
- 受害者定义：击杀记录存在，但对应 checkpoint **无任何分类记录**（= 零分类击杀）。

## 结果：0 受害者（明确结论，非缺省）

- 25 条击杀分布：gate 17（C3 格式 10、不可解析 3、A/B/D 各 1+1+2）、bench 4、
  commercial-triage 3（dossier 不可解析 2、outcompeted 1）、rank 1。
  **`ingest-filtered` 计 0 条，`ingest-gate` 计 0 条**——嫌疑类为空集，无需逐条对照。
- 旁证一（FSM 事件日志全量，`state/events.jsonl`）：历史上 `ingest-filtered` 击杀事件仅发生过
  **1 次**——2026-07-10 17:40:41 的 `pipetest-tick-chain`，即当日管道实测**故意注入**的合成候选
  （活体复现该 bug 的演示本身）；17:44:05 已重新入池、当晚按 FSM 规则善终撤净，killlist 无残留。
  真实候选 4 个（certdeadman/sqlfence 07-08、envpreflight/spendbook 07-10）均在当日 11:00
  **新鲜 checkpoint** 的 tick 入册，全部经真实分类（checkpoint 记录在案）。
- 旁证二：全仓 12 个 ingest checkpoint 共 153 个已分类 id，无一击杀记录落在 checkpoint 覆盖之外。

为什么是 0：该 bug 只在"同日第二次 tick + 恰有新候选到达"时触发；生产 tick 每日仅 11:00 一发，
历史上唯一的同日重 tick 就是 07-10 的管道实测本身。bug 是真的（已活体复现），受害者恰好还没来得及产生。

## 处置

- 解禁/重入：**无对象**（0 受害者）。
- 防回归（本审计新增）：`innovation/commercial/tests/test_no_unclassified_kills.py` ——
  在该 bug 的精确触发条件（同日旧 checkpoint + 新候选）下断言不变量：
  **任何 `ingest-filtered` 击杀必须有对应分类记录**（先被真实分类、判 noise，才允许杀）；
  useful 新候选绝不被 ingest 杀。实测输出：`2 passed`。
- 既有修复的回归（当日已入库）：`tests/innovation/test_ingest_merge.py`（resume=merge 语义，3 例）。

## 诚实边界

- 判定依赖 checkpoint 文件在盘且可读——12/12 全部可读，无一缺失，结论不含推断成分。
- events.jsonl 只覆盖 v1.1 FSM 期（07-08 起）；更早的周批 v1 无 ingest-filtered 代码路径（该击杀
  reason 由 v1.1 tick 引入），故不存在盲区。
