# 内存取证报告：这台 Mac 为什么突然"应用程序内存不足"

**取证时间**：2026-07-03 03:23–03:45（事故二后约 1.5 小时，系统 03:11 刚重启）
**取证方式**：只读。未杀任何进程、未改任何配置。原始数据在 `~/projects/mac-memory-forensics/raw/`。
**标注约定**：[实测] = 本次直接测量；[日志] = 系统日志/诊断文件原文；[推断] = 由证据推理，注明置信度。

## ① 结论一句话

**凶手不是"项目太多"，而是 7 月 1 日新上线的 ai-architect v2 夜间无人值守 runner：它的流水线在夜里产生过一个失控的 python3.13 进程（常驻+压缩 25 GB、生涯峰值 47.3 GB，机器只有 16 GB），两次事故都发生在它的头两个夜间窗口内** [日志+实测]；白天常驻的 Doubao/抖音/Claude 全家桶（合计约 8–10 GB）把底座垫高，让失控进程更快撞墙 [实测+推断]。

## ③ 两次事故的日志证据

### 事故一：Jul 2 凌晨（02:46–02:57 jetsam 风暴 → 03:19 重启）

时间线（全部有文件/日志背书）：
- Jul 1 21:00 v2 第一个 12 小时夜间窗口开启（`launchd-calendar`），runner 由 `caffeinate -i -s` 包裹——**整夜不许睡眠** [日志：window.log + plist]。
- Jul 2 01:41 cycle-14（dotenv2json）开始 [日志：loop.jsonl]。
- Jul 2 02:00:01、02:02:09 kill_test 连续 `kill -9` 两个 pid（旧版误杀缺陷当场发生），02:02:16 runner 被 launchd 拉起复活 [日志：kill-test.jsonl + loop.jsonl]。
- Jul 2 ~02:38 python3.13 (pid 94614) 诞生：首次 jetsam 时 age≈486 秒而 cpuTime≈481 秒——**从出生起 100% 满核烧了 8 分钟** [日志，age 单位换算为推断]。
- Jul 2 02:46:49–02:57:06 **14 个 JetsamEvent 文件**，该 python 从 18.2 GB 涨到 25.3 GB，lifetimeMax 47.34 GB；内核连杀 replayd/assistantd/homed 等几十个小进程，"应用程序内存不足"对话框即此机制 [日志]。
- Jul 2 03:19 关机卡死记录（shutdown_stall）+ 重启；机器停机到 14:24 左右 [日志：wtmp + 诊断文件时间]。

**pid 94614 是谁**：jetsam 不保存命令行，且该时段内核日志已被轮转清除（验证过：连确定发生过的 Jul 2 02:4x jetsam 内核行也查不到了），无法 100% 恢复。但它是 python3.13；全机 python3.13 只有两处——v2 的 venv 和 miniconda base；凌晨 02:38 无人值守，正在跑的只有 v2 cycle-14（dotenv2json 的 harden/变异测试腿），且 02:00–02:02 刚发生误杀+复活的进程混乱。**判定：v2 流水线的 python（cosmic-ray/pytest/harden 子进程，可能已孤儿化）置信度高 [推断]**。

### 插曲：Jul 2 15:18 一次孤立 JetsamEvent [日志]
最大进程仅 Chrome Helper 0.58 GB，压缩器 3.4 GB——白天多应用的普通高压，量级与事故完全不同。**这就是"以前"的日常形态：挤，但没有单一失控者。**

### 事故二：Jul 3 凌晨（02:04 内核 panic → 02:34 swap 耗尽 → 03:10 关机卡死）

- Jul 2 21:00 第二个夜间窗口开启；runner 继续被卡了一整天的 cycle-14（最终 `wall_clock_s: 89214` = **24.8 小时**，`resumed_from_kill: true`，harden 重试 3 次后 failed）[日志：metrics/cycle-0014.json]。
- Jul 3 02:00 计划中的 kill_test **没有留下任何日志**（jsonl/window.log 均无 Jul 3 条目）——系统当时很可能已经卡死 [推断]。
- Jul 3 02:04:51 **内核 panic**：`watchdog timeout: no checkins from watchdogd in 94 seconds` [日志：panic-full-2026-07-03-020451]。watchdog 超时是系统被压到完全失去响应的典型结局；与内存的因果是 [推断]（panic 报告本身不含内存原因）。
- Jul 3 02:05 自动复位（ResetCounter 02:05:02），**02:05:20 launchd 立即拉起 runner 继续跑** [日志：loop.jsonl]。
- Jul 3 02:24–02:34 重启仅 20 分钟后，内核 memorystatus 日志爆出 **3.9 万行/10 分钟**；02:34:16–02:34:43 的 27 秒内**连续 6 次 `sending out-of-application memory knote`**（= 6 次"内存不足"弹窗事件），依次因 "swap exhaustion" 挂起 Claude、WeChat、KDAN PDF、抖音、Terminal、QQMusic，最后 `no victim found (action: 9)` [日志原文]。
- Jul 3 02:28 cycle-14 终于判死，cycle-15（jsonmerge）无缝开始 [日志]。
- Jul 3 03:10 用户关机（shutdown_stall 03:11:06），03:11 重启。**03:13 runner 又自动复活，此刻 cycle-15 的 cosmic-ray 正在跑**（取证期间实测其 pytest worker 150–160 MB/个，串行）。

磁盘有 263 GB 空闲，重启 20 分钟就 swap exhaustion，只能是**分配速度快于 swap 扩展**——与事故一"47 GB 失控分配"画像一致 [推断，中高置信]。

**关于你记忆中的"Jul 2 晚上"**：22:27 确有一次重启 [日志：wtmp]，但 21:00–22:26 窗口内没有任何内核 memorystatus 日志留存，也没有 JetsamEvent 文件。无法证明它是内存事故（日志保留期不足以证伪）。两次确凿的"内存不足"事件实际都在**凌晨 02:3x–02:5x** —— 恰好是夜间窗口深处 [日志]。

## ④ "以前没事，现在出事"——差异到底是什么

**变化点可以精确到小时** [日志+文件时间戳]：

1. **Jul 1 14:05** `~/ai-architect/v2/` 目录创建；**Jul 1 21:00** 第一个 12 小时无人值守夜间窗口开跑。此前机器从 Jun 29 连续运行到 Jul 2 无任何重启；再往前的重启记录稀疏到 4 月、3 月。**第一个 JetsamEvent 文件恰好出现在第一夜（Jul 2 02:46），第二夜再犯（Jul 3）。** 时间相关性无可辩驳。
2. 以前的"多项目并发"是**白天、有人看着、每个占用中等且稳定**（15:18 那次 jetsam 就是它的形态：最大进程 0.58 GB）。v2 带来的是三个质变：
   - **无人值守 + caffeinate**：机器整夜不睡，失控进程有几个小时的时间无限增长，没人会注意到风扇/卡顿；
   - **工作负载本身会制造病态代码**：变异测试逐个运行 219 个故意改坏的程序变体（cycle-14 实测 219 个 mutant [日志：ADEQUACY.json]），harden 循环反复重写实现再全量重测——某个变体/中间实现进入无界分配是这类流水线的已知风险，而 pytest/hypothesis 进程**没有任何内存上限**；
   - **每天 02:00 的 kill -9 混沌测试**：旧版还误杀过无辜进程（脚本注释自供），`kill -9` 孤儿化整棵子进程树后 launchd 再拉起新 runner —— 新旧两套子进程并存 [日志+推断]。
3. 正常时的流水线其实很省：实测 cosmic-ray worker 150–160 MB、runner 40 MB、`claude -p` 200–700 MB，稳态合计 ≈0.5 GB [实测]。**问题不是平均成本，是没有护栏的尾部风险**：一次失控 = 47 GB。
4. **torch 与此无关** [实测]：v2 venv 里根本没有 torch（只有 pytest/cosmic-ray/hypothesis/numpy/gemtest），全机只有 miniconda3 base 装了 torch，夜间没有任何 torch 进程在跑。
5. 底座恶化是从犯：登录项常驻 8–10 GB（Doubao 一家就 3.8 GB/27 进程，外加 claudevm 0.9 GB 开机即起、VS Code Claude 扩展崩溃时同时挂着 2.1.196/2.1.198 两代 5+ 实例共 ≈1 GB）。它们没变多少，但把 16 GB 的容错空间压没了 [实测+推断]。

## ⑤ 修复建议（分级；**本次一个都没有执行**）

> ⚠️ 注意：此刻 RUN_WINDOW 仍有效（到今早 09:00），runner 正在跑 cycle-15 的 cosmic-ray。**今晚/今晨仍有复发条件。**

### 立刻（今天就该做）
1. **给 v2 流水线加内存护栏**（治本）：最简单可靠的是一个 60 秒轮询的 watchdog（launchd 任务或 runner 内置 psutil）——v2 venv 名下任何 python RSS+compressed 超过阈值（建议 6 GB）即 kill 并写日志。cosmic-ray 的 120 秒超时只防"卡住"，防不了"快速吃内存"。
2. **修 kill -9 的孤儿问题**：runner 以进程组运行子进程，kill_test 改杀 `-pgid`（负号杀全组）；runner 复活时先清点并回收上一代遗留的 v2-venv python。
3. **给 cycle 加墙钟上限**：cycle-14 失败重试了 24.8 小时。超过 N 小时（如 4h）强制判死并跳过，不许跨夜滚雪球。
4. **决定今晚是否开窗**：如果护栏没就位，删掉 `~/ai-architect/v2/state/RUN_WINDOW`（runner 的 KeepAlive 依赖此文件，删除即温和停止）——这是你的决定，我没有动它。

### 搬家后（环境调整类）
5. **夜间窗口前清场**：进夜窗时退出 Doubao/抖音/QQMusic/WeChat/Notion 等常驻（夜里它们贡献 ≈6 GB 纯浪费）；或做成 start_window 的前置脚本（提示用户手动关闭）。
6. **正视 16 GB 的硬约束**：要长期跑无人值守变异测试+LLM 子进程，要么换 32 GB+ 的机器，要么把夜间流水线搬到云端/另一台机器，本机只留监控。
7. 精简登录项与 VS Code 旧版扩展实例（崩溃现场两代扩展并存）。

### 可选（锦上添花）
8. runner 每个 leg 开始/结束时记录自身及子进程 RSS 到 metrics——下次出事直接有取证数据。
9. 用 `memory_pressure` 告警（ccam dashboard 里加一条 >70% 压力推送）。
10. 把本报告的 raw/ 数据留档：三次重启已经毁掉两次现场，JetsamEvent 文件是唯一幸存的"案发照片"，系统会定期清理 DiagnosticReports。
