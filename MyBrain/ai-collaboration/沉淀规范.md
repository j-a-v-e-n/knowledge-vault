# 沉淀规范（每次项目结束，AI 按这个标准更新《踩坑速查》和《铁律》）

> 用途：规定"如何总结和沉淀经验"。每个项目结束时，让 AI 读这份，按此标准
> 更新经验库。目的：保证沉淀的是精华、分类清晰，绝不堆成又长又水的一大坨。
> （上次失败就是因为无标准地乱堆，导致越用越乱、AI 干脆忽略。）

## 第一原则：少即是多，门槛要高
- 每一条沉淀都必须"删了会丢失关键信息、留着每个字都在干活"。
- 不写显而易见的废话（"要认真""要测试""要写好代码"）——这种话稀释真正的规则。
- 不写一次性的、不会再遇到的东西。
- 判断标准：这条以后还会用到吗？用到时它能帮我省事/避坑吗？否→不写。

## 第二原则：分类，不叠加
每条新经验，先判断它属于哪一类，放进对应位置，绝不无脑往末尾堆：

1. 是"通用原则"吗（任何项目都适用，如某种协作方式、思维习惯）？
   → 进《铁律》，精炼成一行。但门槛极高，铁律要保持 ~30 行，轻易不加。
   → 且铁律里不许出现具体工具名（工具会变），只写抽象原则/角色。

2. 是"通用工具坑"吗（某工具的坑，多个项目会遇到，如 Kaggle 路径）？
   → 进《踩坑速查》的"通用坑"区。

3. 是"这个项目特有的"吗（如这个项目的环境名、特定数据格式）？
   → 进《踩坑速查》，给这个项目新开一个"项目区"。

4. 是"工具变更"吗（换了执行端/算力/环境）？
   → 只改《踩坑速查》顶部的"当前工具映射"区，不动别处，不动铁律。

## 第三原则：提炼与清理
- 某条"项目特定"的坑，如果发现好几个项目都遇到 → 提升到"通用坑"区。
- 旧项目以后不碰了 → 它的"项目区"可归档或删除，保持文件不臃肿。
- 定期检查：有没有重复的、过时的、可以合并的？有就清理。

## 第四原则：每条的写法
- 一条一句话，直给，不展开。
- 写"坑是什么 + 怎么避"，不写背景故事。
  好例：「Kaggle CLI 挂载路径是 /kaggle/input/datasets/<owner>/<slug>/，用 glob recursive 找」
  坏例：「我们当时在做 classifier 的时候，发现 Kaggle 上传之后找不到文件，后来折腾了
        好几次才发现原来路径不对……」（全是废话背景，删）

## 怎么触发沉淀
项目快结束时，我会说"按沉淀规范更新经验库"。AI 则：
1. 回顾这个项目真正踩过的坑 / 验证过的工作流（只挑会复用的）
2. 按上面"分类"原则，各归各位
3. 写成一句话一条
4. 做完告诉我：往哪几个文件、各加/改了什么（让我能审）
