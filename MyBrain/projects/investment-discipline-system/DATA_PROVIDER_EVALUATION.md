# 数据与纸面执行候选评估

## 目的

把“官方文档说能做什么”和“个人实际使用时会遇到什么”分开，形成正式接入前的判断门槛。本文是调研结论，不是已经完成的供应商选择。

## 本项目必须满足的条件

### 数据

- 能明确区分原始价格、复权价格、分红、拆分和其他公司行动。
- 能保存决策时点可见性、数据获取时间、来源版本、原始响应和校验信息。
- 能处理缺失、修订、退市证券和生存者偏差，而不是静默填补或覆盖旧快照。
- 能提供可解释的基准；正式比较优先使用总回报或明确说明不可交易的代理。
- 使用许可、个人使用范围、缓存和再发布限制清楚。

### 纸面执行

- 纸面和真实端点必须有结构性隔离，默认只能访问纸面环境。
- 成交模型、滑点、市场冲击、队列位置、股息、费用和部分成交的边界必须被记录。
- 订单状态、成交回报、账户状态和本地账本可以对账。
- 连接断开、重复提交、重试、认证过期和服务方修订必须进入失败路径。

## 候选观察

### FRED：保留为原型来源

FRED 的公开序列适合验证“保存来源文件、计算哈希、检查缺失、冻结快照和重跑”。当前使用的序列是价格指数，不包含分红，因此不承担正式总回报基准的职责。

来源：[SP500](https://fred.stlouisfed.org/series/SP500)、[NASDAQCOM](https://fred.stlouisfed.org/series/NASDAQCOM)、[FRED 导出说明](https://fredhelp.stlouisfed.org/fred/graphs/share-my-fred-graph/export-options/)

### yfinance：研究便利工具，不作为正式事实源

yfinance 的维护者明确说明它不是 Yahoo! 背书或审核的官方工具，使用公开接口，定位是研究和教育用途，实际数据使用仍受 Yahoo! 条款约束，并提示接口只面向个人使用。[yfinance README](https://github.com/ranaroussi/yfinance)

这不等于它不能用：它可以作为探索、交叉检查和原型便利层；但本项目不能把它作为唯一的正式历史数据权威，也不能把接口稳定性和许可范围想当然地扩大。

### Tiingo：正式日线数据的候选研究对象

Tiingo 的 EOD 文档描述了原始与复权价格，并显式提供分红和拆分字段；它还说明会对数据做错误检查并处理公司行动相关问题。[Tiingo EOD 文档](https://www.tiingo.com/documentation/end-of-day)

这使它比价格指数更接近正式日线候选，但仍需在本项目中验证：目标股票和 ETF 覆盖、退市历史、快照/修订行为、使用许可、成本、可下载性和长期可复现性。文档中的供应商能力不能替代本地验收。

### Alpaca：未来纸面适配器的第一候选，不是验证权威

Alpaca 官方说明纸面账户是实时行情驱动的模拟，不把市场冲击、延迟滑点、非市价限价单的队列位置、股息等现实因素完整模拟；纸面专用账户的股票实时数据权限还受限于 IEX。[Paper Trading](https://docs.alpaca.markets/us/v1.4.2/docs/paper-trading)

其市场数据文档也把个人 Trading API 与 Broker API 区分开，并说明不同数据计划的覆盖和限制不同。[Market Data API](https://docs.alpaca.markets/us/docs/about-market-data-api)

因此它适合未来做“外部纸面执行适配器和订单对账实验”，但不能替代本地账本、历史检验或基准定义。任何接入都必须保留供应商原始回报，并与本地状态进行对账。

### Interactive Brokers：功能成熟的第二候选，运维复杂度更高

IBKR 的 Client Portal Gateway 要求在同一台机器上通过浏览器完成认证；个人账户的受保护接口依赖已认证的经纪会话，并存在单一活动经纪会话、重新认证、保活和会话过期等约束。[Client Portal API](https://www.interactivebrokers.com/campus/ibkr-api-page/cpapi-v1/)

它可以作为未来的第二适配器研究对象，但不适合在核心原型阶段引入。社区中关于登录、纸面账户和会话冲突的帖子与官方限制方向一致，不过这些帖子只能作为摩擦信号，不能替代官方规范。[IBKR 社区实例](https://www.reddit.com/r/IBKR_Official/comments/1kflu9d)、[IBKR 社区实例](https://www.reddit.com/r/interactivebrokers/comments/1owcw5h)

## 当前判断

- 核心继续保持供应商中立；不把任何外部 API 直接写进风险闸门和账本核心。
- FRED 继续只承担原型管线验证。
- yfinance 只允许作为研究便利层或交叉检查，不作为正式唯一事实源。
- Tiingo 进入正式日线数据候选清单，待本地验收和许可核对后再决定。
- Alpaca 进入未来外部纸面执行适配器候选清单；先验证纸面回报与本地账本对账，再谈接入。
- IBKR 保留为第二候选；在没有解决认证、会话和可持续运行问题前不接入。
- 当前不创建任何真实交易路径；候选适配器即使未来实现，也必须先经过纸面环境、只读检查、对账和故障注入。

## 下一轮验收顺序

先实现供应商无关的 `DataSnapshot`、`DataSource` 和 `ExecutionAdapter` 契约，再用本地夹具模拟缺失、修订、重复提交、部分成交、认证失效和断线重试。契约通过后，才选择一个有明确授权和可验证纸面环境的供应商做适配器实验。

## 证据边界

官方文档支持“供应商宣称的能力与限制”；GitHub 项目说明支持“工具维护者对 yfinance 的定位”；社区帖子只支持“真实用户遇到过相关摩擦”。最终是否采用，必须由本项目自己的保存、重跑、对账和故障注入结果决定。
