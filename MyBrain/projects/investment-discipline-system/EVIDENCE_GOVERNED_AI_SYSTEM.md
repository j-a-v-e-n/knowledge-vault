# 证据约束的目标系统

## 定位

这套系统回答一个比 Prompt、Context、Harness、Loop 或 Graph Engineering 更上层的问题：

> 怎样让一个概率性的 AI，在长期、复杂、高影响的项目中，持续朝已确认目标前进，并且不能用浅层调研、漂亮叙述或自我评价冒充完成？

本项目不以流行术语作为架构起点。任何外部方法都先还原成它解决的底层问题，再决定采用、改造、组合或拒绝。

当前版本是试验性协议。它负责组织目标、证据和工作，不拥有修改验收条件或批准自身完成的权力。

## 顶层保障主张

只有当以下主张都有当前证据支持时，系统才可以宣称某项工作完成：

- 目标一致：产物仍然服务于已确认目标，没有悄然改变问题。
- 研究充分：关键问题、主要方案、反例、争议和未知已达到当前决策所需的覆盖。
- 构造忠实：实现能够追溯到要求和决定，没有只完成容易展示的部分。
- 验证独立：完成判断不只来自原研究者或实现者的自我评价。
- 运行安全：权限、风险闸门、失败路径和不可逆动作符合项目边界。
- 信息新鲜：时效敏感结论经过当前检查，过期证据没有被当作现状。

“系统完成”是这些主张成立后的结论，不是工作循环自己可以直接写出的状态。

## 从基本事实推导设计

| 基本事实 | 推导出的必要设计 |
| --- | --- |
| AI 输出是概率性的，可能自信地犯错 | 主张与证据分离；独立验证；确定性检查 |
| 上下文有限，长任务会遗忘和漂移 | 外部状态；短小入口；阶段性交接；可恢复运行 |
| 复杂目标包含依赖、并行、分支和汇合 | 显式工作依赖图，而不是只靠对话顺序 |
| 执行结果会改变下一步 | 每个节点内部需要观察、行动、验证和修正的反馈循环 |
| 搜索无法证明自己覆盖了未知未知 | 先建问题地图；多路径搜索；引用追踪；覆盖与矛盾审查 |
| 多个代理会传播同一个上游错误 | 原子主张、来源谱系、未经验证的信息隔离、跨节点证据门 |
| 自我审查容易继承原结论的盲点 | 研究、构造、挑战和验收角色分离 |
| 高影响操作的失败代价不对称 | 确定性规则、人类确认点、失败关闭、完整留痕 |
| 外部环境和 AI 方法不断变化 | 差异更新、时效标签、Living Review |

## 系统的七层结构

### 目标与要求图

从最终结果倒推必须成立的子主张。

每个重要目标节点至少记录：

- 它为什么属于最终目标。
- 满足它需要什么可观察结果。
- 哪些边界不可改变。
- 什么证据可以证明它成立。
- 哪些反例会推翻它。

目标图防止项目只完成容易展示的功能，却遗漏真正决定价值的部分。

### 失效图

在设计成功路径之前，先列出系统可能如何“看起来成功、实际失败”。

本项目至少持续检查：

- 问题定义错误或目标漂移。
- 只找到支持原想法的资料。
- 把官方宣传、单个用户经验或模型总结当成事实。
- 关键来源已经过期、被撤回或不适用于当前场景。
- 上游错误被多个代理重复后形成假共识。
- 实现通过局部测试，却没有贯穿真实使用路径。
- 风控在演示路径有效，在实际入口可被绕过。
- 回测、建议或复盘使用了决策时点之后的信息。
- 完成标准由实现者事后降低。

每个高影响失效模式都要对应预防、检测、证据和恢复方式。

### 研究与证据图

研究的正式产物不是一篇流畅报告，而是一组可追溯关系：

- 问题：当前需要回答什么。
- 主张：我们认为成立的原子判断。
- 来源：主张来自哪里、何时取得、属于哪类证据。
- 支持：什么证据支持哪条主张。
- 挑战：什么证据削弱或推翻哪条主张。
- 冲突：哪些来源或结论彼此不一致。
- 未知：仍缺少什么，以及它是否会改变决策。
- 决定：基于哪些证据作出了什么选择。
- 失效条件：什么新信息出现时必须重开决定。

主张状态使用：待验证、部分支持、已支持、受挑战、已否定、已取代。

模型生成的总结、社区帖子和供应商宣传都只能进入“候选证据”，不能自行晋升为项目事实。

### 工作依赖图

任务不是按写下来的顺序执行，而是由尚未满足的保障主张生成。

每个工作节点必须有：

- 输入和允许读取的上下文。
- 单一主要责任。
- 输出契约。
- 权限边界。
- 完成证据。
- 失败出口。
- 可以激活的后续节点。

只有存在真实依赖、并行、分支、隔离或恢复需求时才显式使用图。简单任务保持单循环，避免为了架构名称制造复杂度。

### 节点内反馈循环

每个研究或构造节点内部执行：

> 恢复局部状态 → 选择当前缺口 → 行动 → 观察结果 → 验证 → 更新证据 → 继续、通过或失败

循环不能改变自己的完成标准，也不能把运行次数、篇幅、引用数量或 token 消耗当作质量证明。

### 独立保障层

保障层不负责替原工作润色，而负责尝试证明它不应通过。

它检查：

- 是否遗漏会改变结论的分支。
- 引用是否真的支持相邻主张。
- 是否存在更接近原始事实的来源。
- 不同来源是否只是互相转述同一个上游说法。
- 是否存在反证、撤回、失败案例或不适用边界。
- 实现证据是否覆盖真实入口和失败路径。
- 剩余未知是否足以改变当前决定。

高风险主张必须由与生成者隔离的上下文重新检索或验证。多个角色使用同一份未经核验的摘要，不算独立。

### Living Review

对快速变化的领域，研究结果附带：

- 最后检索时间。
- 时效敏感范围。
- 触发重查的事件。
- 与上次版本相比的新增、变化、失效和不变。

恢复项目时优先做差异扫描，不必每次从零重写全部研究；若新证据改变领域地图、失效模式、工具能力或项目决定，则重新打开相关节点。

## 深度研究协议

### 明确研究服务的决定

先写清：

- 研究结束后要支持什么决定或行动。
- 范围和非范围。
- 哪些答案会改变方向。
- 哪些事实具有时效性。
- 什么叫“足够用于决定”。

没有决定对象的“研究整个领域”，不会自动拥有可判断的终点。

### 建立问题与领域地图

在写结论前先形成覆盖地图：

- 基础概念和共同前提。
- 主要方法、流派和替代方案。
- 已知失败模式和反例。
- 评价基准和可复现实验。
- 工具、实现和真实运行经验。
- 争议、未知和研究前沿。
- 与本项目的适用关系。

领域地图允许随证据扩展，但每次扩展必须说明新节点为何重要。

### 广度检索

按证据类型设计搜索，而不是只换几个相似关键词：

- 官方规范和原始发布。
- 同行评审论文、预印本和公开基准。
- 实际代码、变更记录和问题追踪。
- 普通使用者经验、故障报告和替代工作流。
- 批判性评论、失败案例和反方观点。
- 上游引用、后续引用和相邻领域方法。

社区经验负责发现问题和假设，不能单独证明普遍规律。

### 深度追踪

对会改变决定的节点：

- 回到原始来源，不满足于二次转述。
- 做向后和向前引用追踪。
- 比较来源的对象、时间、样本、基准和限制。
- 主动搜索否定性证据和失败案例。
- 对冲突来源分别保存，不静默选边。
- 必要时通过本地实验复核。

### 原子化主张

先建立主张—证据台账，再写叙述性综合。

每条重要主张至少包含：

- 主张本身。
- 类型：事实、推断、观点或假设。
- 直接来源和取得时间。
- 支持强度及适用范围。
- 反证或冲突。
- 对项目决定的影响。
- 当前状态。

一条引用不能自动支持整段文字。

### 对抗性挑战

挑战者从“如何推翻当前结论”出发，至少执行：

- 缺失分支搜索。
- 来源独立性检查。
- 关键引用核对。
- 反例和失败案例搜索。
- 替代解释。
- 过期与适用性检查。
- 剩余未知的决策影响检查。

挑战结果进入证据状态；不能只作为最后一段免责声明。

### 综合与决定

最终综合必须区分：

- 已有强证据支持的事实。
- 证据有限但当前可采用的判断。
- 相互冲突、需要保留多种解释的部分。
- 当前不知道的部分。
- 采用、试验、延后或拒绝的建议。
- 使决定失效的触发条件。

### 研究完成门

研究开始前必须冻结范围合同、覆盖节点、状态枚举、必查来源类别、查询记录格式、时效截止日、挑战方式和停止预算。每个覆盖节点只能处于 `supported`、`contested`、`no-evidence`、`stale` 或 `out-of-scope`，不得用自由文字隐藏未完成状态。

研究只有在以下可观察条件都满足时才能提交“候选通过”：

- 研究服务的决定、范围和关键问题明确。
- 冻结合同中标为高影响的全部覆盖节点都有上述合法状态。
- 高影响主张可追溯到适当来源，引用与主张逐项相符。
- 合同列明的替代方案、反例、失败案例、负面检索和引文追踪查询均有时间、平台、精确查询和纳入/排除记录。
- 每个高影响主张至少标记上游来源簇；同一新闻稿或数据集的转述只算一条证据链。
- 时效敏感内容的检查日不早于合同规定的截止日。
- 只读挑战者提交了缺失节点、矛盾、引用蕴含和来源独立性结果；所有高影响发现均已解决或转为 `contested`。
- 剩余未知被列出，并说明是否会改变当前决定。
- 预先规定的补充检索轮没有新增高影响覆盖节点或改变采用决定；预算先耗尽时只能标记 `bounded-incomplete`。
- 采用判断包含本项目的验证方式，而不是直接照搬外部结论。

生成者只能提交候选状态。最终通过还需要 L3 确定性校验或明确的人类裁决；任何一项缺失，都只能写“当前证据下的阶段性判断”或 `bounded-incomplete`。

## 构造与验收协议

实现任务从保障主张和失效图生成，不从“容易写什么代码”生成。

每个构造任务必须：

- 链接到目标或要求节点。
- 列出相关失效模式。
- 先检查现成实现和已知问题。
- 规定输入、输出、权限和失败行为。
- 在实现前确定可观察的验收证据。
- 同时验证正常路径、拒绝路径和恢复路径。
- 由独立审查检查需求覆盖、实现漂移和测试盲区。

代码生成、测试通过、界面可见和一次成功运行都不是单独充分条件。

## 当前项目的轻量实现

当前先使用已有能力实现这些原则：

- Codex 持久目标：保存当前阶段目标并自动续行。
- 项目级 `AGENTS.md`：提供每次自动加载的入口与硬约束。
- Obsidian 项目文件：保存章程、状态、决定、证据和工作图。
- 研究与工作模板：把主张、证据、失效模式和完成门变成必填结构。
- 项目代码、测试和运行证据：提供确定性反馈。
- Git：保存可恢复的变更历史。
- 独立代理或独立上下文：只提供 L1 隔离；承担保障职责时还必须使用不同证据路径，并由确定性检查或人类裁决闭合。

当前立即区分四种图：目标/要求图、主张/证据图、工作控制流图和实际执行 trace。关系数据现在就显式保存；是否引入 LangGraph 等可执行图运行时是另一项决定。

暂不因为“Graph Engineering”流行而引入新的图运行时或多代理平台。只有在本地出现以下证据时再评估：

- 任务依赖和并行关系无法由现有看板清楚表达。
- 需要节点级权限隔离、重试、恢复或结构化交接。
- 单一线程的上下文污染导致可复现的质量下降。
- 需要可视化运行状态和完整的跨代理事件谱系。
- 现有 Codex 目标、子代理、项目文件和验证命令无法稳定完成真实任务。

## Codex 与可视化工作台的分工

Codex 可以完成系统的推导、文件维护、代码构造、网页调研、测试、独立代理调度和定期更新，但聊天界面不应成为项目事实的唯一载体，也不适合独自承担大型图的长期交互。

建议把系统分成四个载体：

### Codex：研究与执行引擎

- 读取目标、证据、状态和工作依赖。
- 生成或更新结构化项目数据。
- 执行研究、构造、测试、挑战和状态恢复。
- 使用持久目标维持当前阶段，用独立代理或上下文隔离验证。
- 通过定期任务执行时效扫描和 Living Review。

### 本地结构化存储：事实源

- 目标、节点、边、主张、来源、状态和运行事件保存在可验证的本地结构中。
- 第一阶段可以从 Markdown 表格和 JSON 开始；关系和查询复杂后再迁移到 SQLite。
- 图的屏幕布局不是事实，节点、关系、证据和状态才是事实。
- 所有视图都从同一个事实源生成，避免看板、Canvas 和报告互相不一致。

### Obsidian：长期阅读与人工编辑空间

- 保存章程、决定、研究综合、运行记录和可读交接。
- 可以用开放的 JSON Canvas 生成快速空间视图。
- Canvas 适合讨论和浏览，不作为自动运行状态的唯一真相。

### 本地网页工作台：主要可视化和操作界面

- 分别查看目标与要求、失效、证据、工作依赖和运行时间线。
- 节点可展开查看来源、证明义务、状态、阻塞和下游影响。
- 同一事实源生成不同视图，不把所有关系硬塞进一张巨图。
- 初步候选是 React Flow：适合自定义节点、拖拽、缩放、选择和交互式编辑。
- 若以后需要复杂网络分析，再评估 Cytoscape.js；静态文档快照使用 Mermaid。

### 是否需要额外工具

第一阶段不需要购买外部服务。Codex 可以在当前项目内搭建本地事实源和网页工作台，并继续使用 Obsidian 与 Git。

只有出现以下需求时才考虑额外运行工具：

- 机器或进程崩溃后必须从具体节点自动恢复。
- 工作跨越数天并包含定时器、外部信号、自动重试和幂等副作用。
- 多个并行代理需要严格任务队列、节点级权限和跨进程审计。
- 本地 Codex 持久目标与计划任务无法提供足够的恢复和可观察性。

届时再比较 Temporal、LangGraph、Microsoft Agent Framework 或其他持久工作流，而不是现在预先引入。

## 当前外部证据

- 截至 2026-07-24 的公开检索中，没有找到与近期 “Graph Engineering” 术语传播同步发布的统一模型或技术标准；这是日期限定的暂定推断，而不是对所有发布的否定证明：[概念溯源](https://datasciencedojo.com/blog/graph-engineering-frameworks/)、[批判性核查](https://www.turingpost.com/p/is-graph-engineering-real-why-everyone-is-talking-about-it)。
- Google ADK 已把图工作流定义为节点、边、显式路由、状态和确定性代码与 AI 推理的组合：[Graph-based agent workflows](https://adk.dev/graphs/)。
- Deep Research 代理仍存在明显的检索覆盖和知识组织缺口：[TaxoBench](https://arxiv.org/abs/2601.12369)、[DeepResearch Bench II](https://arxiv.org/abs/2601.08536)。
- 覆盖驱动的目标拆解、依赖控制和基于证据充分性的终止条件，可以减少过早停止：[Don’t Stop Early](https://aclanthology.org/2026.acl-industry.116/)。
- 误导信息可能在长链研究中被吸收为最终结论，局部验证并不能完全消除这一风险：[MisKnow-Agent](https://arxiv.org/abs/2607.20891)。
- 多代理系统会出现级联放大、拓扑敏感和错误共识；未经验证的主张需要在跨节点传播前受到治理：[From Spark to Fire](https://arxiv.org/abs/2603.04474)。
- 系统综述方法强调预先定义问题和纳入标准、广覆盖搜索、引用追踪、可复现记录和偏差审查：[PRISMA 2020](https://www.prisma-statement.org/prisma-2020)、[Cochrane 搜索与筛选指南](https://www.cochrane.org/authors/handbooks-and-manuals/handbook/current/chapter-04)。

## 版本与复核

- 当前版本：第一版。
- 当前状态：试验性、非裁决性的执行基线；只允许组织工作，不能批准自身完成。
- 首个试验：用本协议重新评估 AI 协作、Harness、Loop 和 Graph 方法，并把结果用于下一阶段投研产品工作。
- 复核原则：只有本地证据能决定它是否有效；外部热度和文档完整度不能。
