# Harness 与持续循环方案评估

## 当前问题

我们需要的不是一个“会生成代码”的工具，而是一套能让 AI 在长任务中保持方向、读取状态、验证结果、记录失败并知道何时停止的运行方式。

2026-07-24 复核后，问题进一步明确：Harness 只是证据约束目标系统的执行边界之一。工具选择必须从目标、失效模式和证明义务推导，不能从新术语或框架热度推导。

## 候选方案

| 方案 | 主要能力 | 当前适配度 | 当前结论 |
| --- | --- | --- | --- |
| Codex Goal + 项目 Markdown | 持久目标、跨轮状态、项目文档、工具调用和验证 | 高 | 作为待评估基线，不承担最终裁决 |
| Ralph | 文件型循环、每轮读取磁盘状态、任务状态、进度和错误日志 | 中 | 作为后续本地循环试验对象 |
| OpenHands | 完整的软件工程代理平台、工具系统、代码库操作和治理能力 | 中 | 当前不引入，未来需要更强 Harness 时评估 |
| PROJECTMEM | 追加式事件日志、项目记忆摘要和行动前重复失败提醒 | 中 | 当前先验证是否真的出现重复失败需求 |
| work-buddy | Obsidian、个人工作流、跨会话记忆和任务管理运行时 | 中 | 作为通用项目工作系统候选，不直接采用 |
| Graphroom / AI-GraphAgent | 用 Markdown 定义 Codex 节点、依赖、权限、证据和运行台账 | 中 | 作为 Graph 原型观察，不采用其“已证明”类自我声称 |
| Google ADK / Microsoft Agent Framework / LangGraph | 显式节点、边、状态、条件路由和多代理编排 | 中 | 底层模式成熟；当前项目尚无引入框架的本地必要性证据 |
| Temporal 类持久工作流 | 节点重试、恢复、计时、信号和可审计执行历史 | 低至中 | 只有出现跨进程长期运行和恢复需求时再评估 |

## 采用判断

当前采用“轻量组合”作为待评估基线，而不是已经证明优于外部方案：

- Codex Goal：负责本线程的目标和持续执行；完成判断由冻结合同、确定性检查和独立裁决记录负责。
- Obsidian 项目空间：负责长期状态、任务、决定、研究和循环规格。
- 项目文件与命令：负责实际产物和可重复验证。
- Git：负责变更历史和可恢复性。

这个组合的优点是已经存在、改动小、容易检查，不会在尚未验证需求时增加一个新的代理运行时。现有性只降低迁移成本，不构成效果证据。它的缺口是：循环是否能在长时间离开用户时稳定持续、任务是否需要更结构化的队列、是否需要追加式事件日志，目前还没有本地证据。

当前组合新增两项硬化：

- 项目级 `AGENTS.md` 自动加载恢复顺序、安全边界和完成门。
- `EVIDENCE_GOVERNED_AI_SYSTEM.md` 与研究/工作模板把目标、失效、证据、依赖和独立保障显式化。

当前结论不是“永远不用 Graph”，而是先使用图的底层纪律，不先承担图框架的运行复杂度。

## 选择外部工具的触发条件

只有出现以下实际缺口时，才引入额外工具：

- Codex Goal 无法稳定维持当前任务的连续推进。
- 需要多个独立任务自动排队、重试和恢复。
- Markdown 状态无法防止重复失败或无法提供足够的审计记录。
- 需要隔离工作树、并行代理或更复杂的工具权限。
- 需要把这套工作系统抽象为可供多个项目接入的产品。

## 本地试验要求

引入任何候选工具前，先用一个小而真实的项目任务测试：

- 能否从项目文件恢复状态。
- 能否只推进被授权的任务。
- 能否在失败后记录原因并改变策略。
- 能否运行独立验证而不是自我宣布成功。
- 能否在达到完成标准或触发暂停条件时停止。
- 是否增加了超过其价值的维护、权限和上下文负担。
- 在相同任务、权限、输入、完成标准和预算下，相比当前基线的恢复率、重复失败、人工介入、工具调用、耗时和维护负担。

目前没有证据证明需要安装外部 Harness，因此本轮不安装。
