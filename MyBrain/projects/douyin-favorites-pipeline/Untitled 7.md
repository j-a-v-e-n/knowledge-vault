一个团队里面如果既有人类的同事，又有 AI agent 团队合作应该怎么设计？上周我正好去北京参加了出门问问的发布会，他们发布了一个新的产品叫做 CodeBanana。从表面上来看它也是一个 code agent 写代码的智能体，比如读项目、改文件、跑命令、提交代码这些都能做，现在已经不稀奇了。像 Cloud Code、Open Cloud Cursor 大家平时其实已经都在用了，CodeBanana 真的有意思的点是解决了另一个问题，如果一个团队里面又有人，每个人又有自己的 agent 项目，本身也是 agent，甚至不同项目的 agent 还能互相加入讨论复杂的写作关系应该怎么去设计？我觉得 CodeBanana 给了我们一个挺有意思的答案。所以这期视频就来仔细的看一下产品，讨论一下团队合作的问题。当 AI agent 进入团队之后产品形态会变成怎么样？团队合作又会变成怎么样？

这个就是 CodeBanana 的工作界面。CodeBanana 有个基本单位就是 project 项目，这个项目更像是一个容器，里面可以有代码、agent、聊天、get、云端的执行环境，也有成员的权限、项目的上下文。每个项目默认只能自己看到，但也可以邀请同一个组织里面其他成员来加入。每个项目还可以看到它有独立的配置，比如独立的 agents 点 md、搜点 md、user 点 md，还有 skills 的文件夹。简单说每个 project 都可以有一个独立的 agent，它有自己的身份、有自己的提示词、技能上下文。每个人还会被分配到一台 VPS，就是云端的开发环境，代码可以在里面跑，agent 也可以在里面去执行任务。所以看到这个界面结构之后可以想到 CodeBanana 背后的思想就是想把项目、agent 聊天、云端环境 get 全部都放进同一个工作流里面。

右边看到有 CodeBanana 的三个关键的入口。第一个就是 private ask，顾名思义就是私人对话，就是跟项目 agent 去单独聊天的内容。第二个是这里的 discussion，比较像现在办公软件里面的项目群聊，团队成员可以在这里面去讨论需求方案进度。第三个是 team agent，这个是项目里面的公共的 agent 对话，所有的项目成员在这里可以看到公共对话的同一份内容，谁给 agent 发了什么东西，agent 怎么执行的、怎么回复的，最后改了哪些文件大家都能去同步看到。这三个入口就对应了平时的三种工作状态。private ask 就是个人的思考。discussion 就是团队的共识。team agent 就是公共的执行的区域。如果把这三层都跑顺了，其实平时的想法到沟通就能更自然地变成落地执行的工作。

大家可以想一想，其实很多团队不是不沟通，而是沟通完了之后还是有很多搬运、落地的执行的工作，群里定了一个事情，再切到 app 去改代码，然后再打开终端去跑命令，最后再去 get 提交。中间的过程非常的长，CodeBanana 想减少的就是中间来回切换，来回倒腾的成本，把讨论执行记录都留在同一个项目里面。

举个例子看看 CodeBanana 到底是如何来具体解决团队当中的工作流的。假设这里有两个项目，一个叫做 website launch，它是专门用来负责官网开发上线的项目。看到里面有官网的首页的代码，资源文件对应的 agent。另外一个就是 policy review 项目负责规则的说明，也有项目 policy review 对应的 agent。现在是什么问题？现在问题就是官网上面有这样一句话：每个开发者永久免费。听着很爽，但问题是产品确实每个月是免费的，但免费版只有每个月三十次的使用量。这句话能不能写？

就以这个很日常、很具体的问题作为例子，看看在 CodeBanana 里面一个团队流程应该是怎么去做的。第一步，我会先在 website launch 项目里面，他的 private ask 里面去问一下，我会直接问他，然后帮我分析这句每个开发者永久免费这句话有没有风险，让开发项目的 agent 先帮我去想一轮。他可能会提醒我说每个开发者永久免费这句话容易被理解成无限的免费，但真实的规则每个月只有三十次，所以应该表达的更清楚一点。

第二步，我会直接用转发功能把刚刚这段分析直接转发到 website launch 去讨论区。这一步其实就很像平时的真实的工作场景了，就是自己先想一下，想完以后把结论丢到团队里面去对齐。不成熟的想法不用一开始就公开，关键的判断也不会永远藏在自己的私人的聊天记录里面。

第三步，在团队的讨论区里面大家会继续讨论，比如营销的人可能会说永久免费更有吸引力，产品的人可能会说可以保留免费，但必须在下面一行小字里面写清楚，说每个月三十四的使用量。具体的讨论结果我觉不重要，因为这项目里面其实也没有什么其他团队成员。我觉重点是分析说 CodeBanana 帮助我们去解决问题的工作流程，人的讨论跟 AI 的分析进入了同一个项目之后应该怎么去做信息的流转分配，不用在微信里面去聊一半，然后在办公软件里面去聊另外一半，最后在 id 里面去写另外一些代码，最后谁也不知道结论从哪里来的，又要往哪里去。

第四步，我觉得是最有意思的，就是可以把 policy review project agent 邀请进来官网开发项目，直接点这里的添加邀请，它仍然是 policy review agent 这样的身份，也带着原来的知识背景 skill，它可以进入到官网开发项目，参与讨论，也可以访问官网。开发项目里面的所有这些文件，这就非常的 aliennative 了。为什么？就是以前的 agent 塔是一个工具，现在它更像一个协助对象，更像一个你们公司的法务的顾问这样的角色。它有自己项目的身份，有上下文，有技能，也有访问的边界。你可以把它从另外一个项目里面拉进来，让它以政策审核专家的身份继续参与你们这个项目的讨论。比如说在这里，我把它拉进来之后，我就可以问他，请检查轰配置点 md 里面每一个开发者永久免费这句话是否跟定价策略一致。如果有风险，可以给出更安全的、可替代的这种表达，直接发送给他，因为他有着合规方面的技能，然后会给出更加专业的判断。但是最后还是可以人类的成员去负责取舍判断，最后让这个 website agent 去负责执行修改。这整个过程项目成员都可以去看到、去同步。

我们看到这整个流程已经不太像传统的 AI 的 ide，只能写代码。它更像一个小的团队里面有不同的角色，不同的上下文不同专业背景的这种 agent。

如果我们进一步去思考，这种合作的本质是什么？过去团队里面的知识主要放在人脑里、文档里、代码里面。某个产品经理可能知道定价规则，飞书或钉钉里面写着政策的说明，仓库里面有一些业务逻辑。当 agent 进入团队之后，这些知识会变成这可以被邀请的这种角色。比如说之前的 policy review agent 代表了政策的口径，website agent 代表了当前这个项目实现的执行者，他没有去代替原来的产品法务开发，他更像是这些角色背后的知识更顺畅地进入了开发的项目的流程里面。

当然我觉得当下这个产品设计会带来一些新的问题。比如说第一个就是入口变多了，什么问题先私下问，什么内容可以发群聊，里面什么问题可以发给 team agent 的执行团队，必须先形成共识，否则这个信息就会很乱。第二点就是 agent 虽然可以在知识层面上或者是执行层面上像人类员工一样出现，但它不能像人类员工一样去负责任，他可以参与讨论，可以修改文件，可以给建议。但最后出问题了，责任还在人类团队身上。第三点就是 agent 最可怕的就是上下文混乱，每个 agent 都有自己的项目背景规则记忆。如果边界不定义清楚，他们看起来是在写作可，实际上就是拿不同的版本的信息其实在互相的干扰、互相的讨论。

所以整个使用下来我对 CodeBanana 的判断是大家看 agent 本身其实跟 Cloud Code、Codex、Open Cloud 其实没有太大的区别。因为现在的使用的 AI 工具已经对个人的帮助已经非常明确、比较成熟了，这个时代也在建立起一个个的超级个体。更关键的问题就是 AI 进入了团队之后，进入了企业之后整个团队的工作流怎么定义？整个组织怎么去定义？这些问题恰恰就是《超级组织》这本书在系统讨论的 AI 进入组织之后，协助关系信息流动，全责边界到底是怎么样设计的？

CodeBanana 不一定给出了最终的完美的答案，但我觉得是对下一代的 AI 开发工具，下一代的 AI 团队协助工具，一次很好的探索跟尝试。
